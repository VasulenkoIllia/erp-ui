# erp-ui — специфікація UI-кіта для ERP/CRM-систем

> **Статус:** узгоджено, версія 1.0 від 12.10.2026. Це нормативний документ: що тут записано як рішення, команда виконує без повторного обговорення. Зміни вносяться через ADR (`docs/adr/`).
>
> **Як читати.** Розділи 1–6 — рішення й правила, 7–11 — як мають працювати екрани, 12–16 — що будуємо і в якому порядку, 17–20 — як працюємо. Детальні обґрунтування й джерела лежать у `docs/research/`.
>
> **Ідентифікатори.** Модулі `A1…T1`, компоненти `UI01…UI47`, платформні можливості `PF01…PF20`, локальні модулі `LC01…LC12`. Ті самі ID використовуються в коді, задачах і комітах.

## 1. Мета і межі

**erp-ui** — власний приватний реєстр компонентів, шаблонів сторінок і модулів, з якого будуються всі CRM/ERP-проекти студії. Мета: кожна нова система виглядає однаково, стильно й практично, працює на телефоні, планшеті й десктопі, а елементи беруться з одного місця.

Що входить:
- токени й теми (5 палітр, світла й темна, дві щільності);
- примітиви на shadcn/ui;
- ERP-компоненти (таблиці, фільтри, стрічка запису, редактор рядків, канбан тощо);
- шаблони сторінок;
- модулі з TypeScript-контрактами API й мок-сервером;
- демо-застосунок, де все це живе разом;
- правила й скіл для Claude Code.

Що **не** входить:
- бекенд (кіт лише фронтендовий; бекенд кожного проекту пишеться під контракти кіта);
- польська мова інтерфейсу (не плануємо; див. розділ 11);
- платні бібліотеки в основі (лише під конкретного клієнта, див. розділ 5).

Застосування:
- нові проекти стартують одразу на erp-ui;
- старі (project-a, project-b, project-c тощо) переводяться лише під час великих доробок;
- з кітом працюють автор і інші розробники команди.

## 3. Архітектура

### 3.1 П'ять шарів реєстру

| Шар | Що входить | Правило |
|---|---|---|
| 1. Токени й теми | `themes.css`, щільність, радіуси, `--chart-*`, статусні кольори | значення генеруються з `design/palette-tokens.json`, руками не правимо |
| 2. Примітиви | shadcn/ui на Base UI | зміни лише через реєстр |
| 3. ERP-компоненти | UI01–UI47 і платформні PF01–PF20 | не залежать від ra-core, крім CRUD-обгорток |
| 4. Шаблони сторінок | List Report, Object Page, Worklist, Overview, Wizard, Split/FCL, Board, Runner, Kiosk | екрани модулів збираються лише з шаблонів |
| 5. Модулі | A1…T1, LC01…LC12 | кожен: контракт + моки + екрани + стани + i18n |

### 3.2 Репозиторій `erp-ui` (приватний)

Пропонована структура (pnpm workspace):

```
erp-ui/
  registry.json                # маніфест shadcn-реєстру
  registry/
    tokens/                    # themes.css, density, fonts
    ui/                        # примітиви (shadcn на Base UI)
    erp/                       # ERP-компоненти UI01–UI47, PF*
    templates/                 # шаблони сторінок
    modules/<ID>-<name>/       # модулі: components, pages, contract.ts, mocks.ts, i18n
    claude/                    # CLAUDE.project.md + .claude/skills/erp-ui (ставиться в проекти)
  apps/demo/                   # демо-застосунок: усі модулі на MSW, стрес-сторінка
  design/                      # palette-tokens.json, генератор themes.css, звіт контрасту
  docs/                        # SPEC.md (цей документ), ADR, CHANGELOG
  CLAUDE.md
```

### 3.3 Доставка в проекти й оновлення

- Підключення в проекті: `npx shadcn add VasulenkoIllia/erp-ui/<елемент>[#vX.Y.Z]` — приватний GitHub-репозиторій як реєстр-джерело (shadcn з серпня 2026 року). Доступ — `gh auth login` або `GH_TOKEN` (fine-grained, Contents: Read-only); у репозиторії проекту токен не зберігається. Структура, назви й правила — ADR-0004, посібник — `docs/using-erp-ui.md`, перелік — `docs/CATALOG.md`.
- Кожен проект отримує код у себе. Ніяких runtime-залежностей від приватних пакетів, тож клієнту можна передати систему повністю.
- Оновлення: `shadcn add … --diff` (перегляд), потім `shadcn add …`. Локальні правки елементів спільних шарів (`ui/*`, `erp/*`, `templates/*`, `lib/*`, `hooks/*`) у проекті позначаються коментарем `// erp-ui: local override — <причина>`, щоб їх не затерти.
- Модулі під клієнта не правляться: поля, колонки, статуси, вкладки й секції клієнта лежать в окремому файлі розширення проекту, тож оновлення модуля ставиться без ручного зведення (ADR-0020). Зміни — дані з ключами (додати, сховати, переставити) і компоненти проекту в слотах: `lib/extensions`, `lib/extension-fields`.
- Вдалий компонент, що з'явився в проекті, переноситься назад у реєстр. Claude Code пропонує це сам (див. скіл).
- Реєстр **приватний**.

### 3.4 Контракти й моки (коротко; повністю — розділ 17)

Кожен модуль постачає `contract.ts` (типи + zod-схеми запитів і відповідей), `mocks.ts` (MSW-обробники зі сценаріями) і демо-дані. UI працює без бекенду; бекенд проекту реалізує той самий контракт.

## 6. Візуальна мова

### 6.1 Палітри

| ID | Назва | Характер | Основний (світла) | Основний (темна) |
|---|---|---|---|---|
| `sapphire` | **Сапфір** (основна) | класичний корпоративний синій | `oklch(0.53 0.2 262)` | `oklch(0.72 0.14 255)` |
| `graphite` | **Графіт** (основна) | монохром, мінімалізм | `oklch(0.22 0.006 270)` | `oklch(0.94 0.004 270)` |
| `indigo` | Індиго | сучасний SaaS | `oklch(0.51 0.22 277)` | `oklch(0.73 0.13 280)` |
| `teal` | Бірюза | спокійний, фінанси й облік | `oklch(0.5 0.09 192)` | `oklch(0.75 0.11 185)` |
| `terracotta` | Теракота | теплий, енергійний | `oklch(0.55 0.17 40)` | `oklch(0.75 0.14 52)` |

Правила:
- Палітри відрізняються **лише** основним кольором, відтінком нейтральних і порядком кольорів графіків. Структура токенів однакова, тому будь-яка палітра вмикається в будь-якому проекті.
- Основний колір ніколи не червоний, зелений чи жовтий: ці кольори зайняті статусами.
- У темній темі основна кнопка світла з темним текстом — так основний колір проходить контраст і як заливка, і як текст.
- Темний сайдбар у світлій темі — опція (`data-sidebar="dark"`). У темній темі сайдбар завжди темний.
- Готові значення: `design/themes.css` (OKLCH, формат shadcn), генерується з `design/palette-tokens.json` скриптом `pnpm themes`. Перевірка: `pnpm check:contrast` і `design/palette-contrast-report.json` (370 пар, 0 помилок).

### 6.2 Перемикання тем

- На `<html>`: `data-palette="sapphire|indigo|graphite|teal|terracotta"`, клас `dark`, `data-sidebar="dark"`, `data-density="compact"`.
- Адмін задає палітру компанії в налаштуваннях компанії. Користувач у профілі може змінити собі палітру, тему (світла / темна / як у системі) і щільність.
- Вподобання зберігаються на **сервері** (контракт PF11); localStorage ra-core — лише кеш, бо він очищається під час виходу.
- Без збереженого вибору тема слідує `prefers-color-scheme`.

### 6.3 Статусні кольори (однакові в усіх палітрах)

| Роль | Призначення | Токени |
|---|---|---|
| success | оплачено, виконано, активний | `--success`, `--success-foreground`, `--success-soft` |
| warning | частково, увага, заблоковано іншим | `--warning`, `--warning-foreground`, `--warning-soft` |
| destructive | помилка, прострочено, видалення | `--destructive`, `--destructive-foreground`, `--destructive-soft` |
| info | очікує, інформація | `--info`, `--info-foreground`, `--info-soft` |

Статус ніколи не передається лише кольором: завжди іконка + підпис. Бейдж = `*-soft` фон + `*-foreground` текст.

### 6.4 Графіки

- 5 категоріальних кольорів `--chart-1…5`; порядок фіксований для кожної палітри й перевірений на розрізненість для дальтоніків (суміжні пари).
- Колір іде за сутністю, а не за рангом; фільтр не перефарбовує решту серій.
- Для ≥ 2 серій — легенда, для ≤ 4 — ще й підписи на графіку; є перегляд таблицею.
- Одна вісь Y; ніяких двох шкал.
- Статусні кольори не використовуються як кольори серій.
- Canvas-бібліотеки (ECharts) отримують значення токенів через хелпер, що читає CSS-змінні.

### 6.5 Типографіка, форма, щільність, іконки

- Шрифт **Geist** (400/500/600/700), підключається з `@fontsource/geist`; числа в таблицях — `tabular-nums`.
- Базовий розмір 14 px; заголовок сторінки 24 px/600; заголовки карток 14 px/600.
- Радіус `--radius: 0.5rem` (8 px); бейджі й чипи — повністю заокруглені.
- Щільність: звичайна (рядок ~44 px, контрол 36 px, цілі дотику 44 px) і компактна (рядок 32 px, контрол 32 px, цілі ≥ 24 px). На одній сторінці режими не змішуються.
- Рамка полів вводу — `--input` з контрастом ≥ 3:1 (свідомо темніша за дефолт shadcn), рамки карток — `--border`.
- Іконки — lucide, обведення 2 (`IconProvider`, ADR-0008); поняття → іконка — лише зі словника `lib/icons`; гривня — `HryvniaIcon`; у кнопках-іконках обов'язковий `aria-label`.
- Стиль оболонки: спокійний, щільний, у дусі Linear — оболонка приглушена, колір лише в діях і статусах. Без градієнтів і «скляних» ефектів.

### 6.6 Рух

- Анімації лише функціональні — пояснюють зміну: поява й зникнення, розгортання рядків і груп, підсвітка щойно зміненого чи доданого рядка, лічильники й прогрес, скелетон → дані, перенесення в канбані. Без декору.
- Тривалості — токени `duration-fast` (150 мс: кольори, меню, підказки), `duration-base` (200 мс: панелі, розгортання), `duration-slow` (250 мс: шторки й великі поверхні); криві — `ease-standard` (зміна на місці), `ease-enter` (поява), `ease-exit` (зникнення). Сирі `duration-200`, `ease-linear` і `transition-all` заборонені (`check-tokens`).
- `prefers-reduced-motion` вимикає рух повністю.
- Інструмент — CSS і View Transitions без бібліотеки анімацій (ADR-0009).

## 8. Стани

Стани рівня екрана не дає жодна бібліотека; вони — найцінніша частина реєстру. Кожен компонент і шаблон документує свої стани в демо-застосунку.

### 8.1 Обов'язкові стани колекції (таблиця, канбан, календар, стрічка, чат)

1. до першого пошуку (якщо список вимагає умов);
2. первинне завантаження — скелетон у формі контенту;
3. оновлення з видимими даними (індикатор без блокування);
4. дозавантаження/пагінація;
5. порожньо вперше — пояснення + дія «Створити»;
6. нічого не знайдено — лічильник «0 збігів» + «Скинути фільтри»;
7. помилка завантаження — повідомлення + «Спробувати ще»;
8. частковий збій (частина віджетів/рядків) з повтором;
9. немає доступу;
10. офлайн / немає з'єднання;
11. застарілі дані — мітка «Оновлено о…» + оновити;
12. вибір: «сторінка» чи «усе» з лічильником між сторінками;
13. масова операція в процесі (прогрес, можна піти зі сторінки);
14. масова операція з частковою невдачею (підсумок + повтор);
15. рядок/картка заблоковані іншим користувачем;
16. оптимістичне оновлення та відкат з поясненням;
17. режим лише для читання.

Порожній стан **ніколи** не підміняє помилку.

### 8.2 Пороги й правила

- Затримка до 1 с — без індикатора; 1–10 с — спінер/скелетон; понад 10 с — прогрес-бар, і користувач може працювати далі.
- Скелетони — лише в контейнерах (таблиці, картки, плитки), ніколи в тостах, меню чи модалках.
- Тости зникають самі лише для некритичних повідомлень без дій (~8 с); з дією «Скасувати» — до взаємодії.
- Видалення — три рівні: без діалогу з «Скасувати»; просте підтвердження; введення слова для критичного. Кнопки називають наслідок («Видалити 3 рахунки»), а не «Так/Ні».
- Незбережені зміни: модальне вікно в застосунку + `beforeunload`, без «більше не показувати».
- Блокування: «Редагує [ім'я]» з режимом перегляду (за зразком Fiori locking).
- Конфлікт збереження («хтось зберіг, поки ви редагували»): власний діалог із порівнянням значень — проектуємо самі, публічного зразка немає.
- Оптимістичні оновлення — через `useOptimistic` (React 19) з автоматичним відкатом.

### 8.3 Поля форм

- Стани поля: звичайний, фокус (кільце `--ring`), помилка, асинхронна перевірка, «змінено», «автозбережено», лише читання, заблоковано іншим, вимкнено.
- **Read-only, а не disabled** для полів, недоступних через права: read-only лишається у фокусі й читається скрінрідером.
- Валідація: при виході з поля → під час виправлення → при відправці. Довгі форми мають зведення помилок угорі з переходом до поля. Кнопка «Зберегти» ніколи не вимикається.
- Серверні помилки прив'язуються до полів; введені дані не губляться.
- Підписи над полями, без фіксованої ширини (переклади довші).

### 8.4 Дії, недоступні через права

- Модуль чи розділ без доступу — **приховується** з навігації.
- Дія в межах доступного екрана — **показується неактивною з підказкою-причиною** («Доступно для ролі Бухгалтер»).
- Цю політику застосовуємо однаково в усьому реєстрі (компонент PermissionGate).

## 9. Адаптив

- Компоненти реагують на **ширину контейнера** (`@container` у Tailwind v4), а не вікна: та сама таблиця може мати 1400 px на весь екран і 450 px у третині FCL.
- Контрольні ширини: телефон 360–390 px, планшет 768 px, десктоп 1280–1440 px.
- **Таблиці.**
  - Колонки задаються декларативно: пріоритет, поведінка («лишити», «перенести під рядок», «сховати»), липка колонка-ідентифікатор.
  - На телефоні таблиця перетворюється на картки.
  - На планшеті — горизонтальна прокрутка з липкою першою колонкою.
- **Фільтри** на телефоні відкриваються в нижній шторці з кнопкою «Застосувати».
- **Форми й піккери** на телефоні відкриваються в нижній шторці (UI38).
- **Канбан:**
  - на телефоні — одна колонка з перемикачем;
  - перенесення картки є також через меню «Перемістити в…».
- **Календар** на телефоні показується списком або по одному дню.
- **Лише для планшета й десктопа:** Gantt, таймлайн ресурсів, спредшит, конструктор процесів і дашбордів, банківська звірка. На телефоні замість них — режим перегляду.
- **Окремі мобільні сценарії для польових ролей:** сканування на складі, день техніка з картою, табель-кіоск, фото чеків.
- **PWA** для всіх проектів. **Офлайн** (UI30) — лише в модулях, де він увімкнений явно (POS, WMS, виїзний сервіс, табель).
- Цілі дотику ≥ 44 px у звичайній щільності, ≥ 24 px у компактній.

## 10. Доступність

- Рівень **WCAG 2.2 AA** для всього реєстру; перевірка axe в тестах і ручна перевірка клавіатурою.
- 2.5.7 (перетягування): кожна дія перетягуванням має альтернативу — канбан, Gantt, планувальник, дерево, порядок колонок, дашборди, зони завантаження.
- 2.5.8 (розмір цілі): мінімум 24×24 px.
- 2.4.11 (фокус не перекривається): липкі панелі не закривають елемент у фокусі.
- 3.3.7 і 3.3.8: не просити повторно введені дані; вхід без когнітивних тестів.
- Грід — за моделлю W3C APG: одна зупинка Tab, стрілки, Home/End, Enter/F2, Esc, `aria-rowcount`, `aria-sort`.
- Контраст: текст ≥ 4.5:1, великий текст і елементи інтерфейсу ≥ 3:1 — уже закладено в палітри.
- `forced-colors` і `prefers-reduced-motion` підтримуються.
- Справжні `<button>`, `<a href>`, `<label>`; ніяких `onClick` на `div`.

## 11. Мови та формати

- Мови інтерфейсу: **українська** (основна й за замовчуванням, мову браузера не враховуємо) і **англійська** з британськими форматами (en-GB). Польська не планується. Помилки провайдерів (зокрема KSeF) показуються як сирий текст провайдера поруч із нормалізованим статусом українською/англійською.
- i18next із ключами форм множини `_one/_few/_many/_other`; усе форматування — через `Intl`.
- Тестові числа для множини: 1, 2, 5, 11, 21, 22, 25, 101.
- Числа: `1 234,5`; розділювач груп — нерозривний пробіл; символ валюти після суми: `48 600,00 ₴`; іноземні валюти — кодом: `1 200,00 USD` (ADR-0007).
- Дати:
  - формат дати задається явно (короткий формат uk дає двозначний рік);
  - у заголовках календаря місяць у називному відмінку («жовтень 2026»), у датах — у родовому («11 жовтня»);
  - тиждень починається з понеділка, номери тижнів — за ISO;
  - час 24-годинний.
- Мову інтерфейсу тримаємо окремо від мови даних і друкованих документів.
- Довжина рядків після перекладу може зрости на 200–300%: жодних фіксованих ширин у кнопках і вкладках.
- Локальні формати й валідатори (LC12): ЄДРПОУ (8), РНОКПП (10), ІПН платника ПДВ (12), IBAN UA (29), телефон +380.
- Документні формати (журнал 1.6): сума прописом (uk, en; гривня, долар, євро в усіх відмінках), ПІБ у родовому відмінку («в особі директора Коваль Олени Вікторівни»), підпис «Олена КОВАЛЬ», ініціали «Коваль О. В.».
- Часові пояси (журнал 1.6): пояс компанії й користувача, події з власним поясом, підказка «у Києві 14:00 / у Варшаві 13:00», годинник фірми в топбарі; дати документів — календарні, без поясу.
- Польська мова інтерфейсу — перед першим польським проектом окремим кроком (§20, №10); інфраструктура мов уже готова.

## 16. Порядок побудови: шість хвиль

Правило: **модуль береться в роботу лише тоді, коли всі його компоненти вже є в реєстрі.** Нова потреба йде в спільний шар, а не всередину модуля. Кожна хвиля починається з пілотного модуля, який змушує створити нові спільні компоненти; модулі-послідовники їх перевикористовують. Для клієнта складського, виробничого чи роздрібного раннер, кіоск і касу можна підняти вище, але через реєстр.

Обсяг (рішення власника 15.10.2026, журнал 1.18):
- **хвилі 0–2 будуються за планом** — з них складається основа будь-якого проекту студії;
- **хвилі 3–6 — лише під замовлення конкретного проекту**: модуль цих хвиль береться в роботу, коли його потребує проект студії, за тими самими правилами (компоненти — спершу в реєстрі, модуль тонкий, зміни під клієнта — у файлі розширення проекту, ADR-0020). Склад і порядок цих хвиль у таблиці — довідкові: вони показують, які спільні компоненти потрібні модулю і в якій послідовності їх будувати. На складі модулів не тримаємо.

Пілот хвилі 1 — модуль B1 у кіті разом з окремим тестовим проектом, який перевіряє встановлення, підлаштування під клієнта без правки файлів модуля, справжній бекенд через адаптер (ADR-0021) і оновлення модуля; клієнтські проекти не змінюються (`docs/WAVE-1.md`).

## 17. Контракти API і моки

Кожен модуль у `registry/modules/<ID>-<name>/` містить:

| Файл | Зміст |
|---|---|
| `contract.ts` | типи й zod-схеми сутностей, запитів, відповідей і помилок; ендпоінти REST за ADR-0002 (ресурсний стиль, сумісний із dataProvider ra-core); події реального часу, якщо є |
| `mocks.ts` | MSW-обробники, що перевіряють права, з перемикачем сценаріїв: `success`, `error`, `empty`, `slow`, `conflict`, `forbidden`, `offline`; для інтеграцій — також сценарії з датою дії |
| `fixtures.ts` | демо-дані українською й англійською; вони ж — шаблони даних для першого запуску (PF12) |
| `i18n/uk.json`, `i18n/en.json` | усі рядки модуля |
| `pages/`, `components/` | екрани з шаблонів розділу 7 |
| `README.md` | призначення, ID, залежності від UI/PF, що реалізує бекенд |
| `index.ts` | точка входу: ресурси, маршрути й пункти навігації модуля з урахуванням розширення проекту; тип розширення — публічний API модуля (ADR-0020) |

Конвенції (ADR-0002, ADR-0003):
- Ресурси — `/api/v1/<ресурс>`: `GET` список і запис, `POST`, `PATCH` (лише змінені поля), `DELETE`. Запис (`GET /:id`, а також відповіді `POST` і `PATCH`) — детальний, з вкладеними колекціями (рядки документа); список їх не віддає (ADR-0019).
- Список — плоскі параметри: `status=paid&status=sent&amount_gte=10000&q=…&sort=-date,number&page=2&perPage=50`; відповідь — `{ data, total }`.
- Помилки мають єдиний формат: `{ code, message, fieldErrors?, providerCode?, providerMessage?, current? }`.
- Гроші — цілі мінорні одиниці + код валюти; дати — ISO 8601 в UTC, форматування лише на клієнті.
- Конкурентне редагування — через версію запису (`version`): розбіжність → 409 `conflict` з `current` і діалог із розділу 8.2.
- Компанія — заголовок `X-Company-Id`; сесія — httpOnly cookie + 2FA; профіль, ролі й права — `GET /me`.
- Вподобання користувача (палітра, тема, щільність, мова) — окремий контракт PF11 (`/me/preferences`), на сервері; особисті збережені види списків — ресурс `/me/views` того ж PF11 (ADR-0017); розмір сторінки списку — `/me/list-settings/<ресурс>` (ADR-0024).
- Закріплення записів угорі списку — `PUT`/`DELETE /<ресурс>/:id/pin` (204, ідемпотентні, право на читання); список і запис віддають `pinned: true`, закріплені — першим блоком у порядку закріплення поверх `sort`, `total` не змінюється; понад 50 — 422 `pin_limit` (ADR-0024).
- Масова дія — фонова задача сервера: `POST /<ресурс>/bulk/<дія>` з `{ ids }` або `{ filter, exclude? }` (плоскі фільтри списку) → 202 `{ jobId }`; стан — `GET /jobs/:id` (прогрес, невдачі групами за кодом причини з першими 20 записами), повтор невдач, які можна повторити, — `POST /jobs/:id/retry` → 202 `{ jobId }` нової задачі (ADR-0018).
- Перемикач сценаріїв моків доступний у демо-застосунку (панель розробника) і в тестах.
- Новий бекенд пишеться під цей контракт. Наявний бекенд з іншим контрактом підключається адаптером у проекті: обгортки dataProvider і authProvider над провайдерами кіта перекладають запити, відповіді, помилки й вхід; модулі й моки лишаються на контракті кіта (ADR-0021).
- Реалізація в кіті: `lib/api`, `lib/data-provider`, `lib/auth`, `lib/preferences`, `lib/mocks`, `lib/mock-scenarios`, `lib/jobs`, `lib/mock-jobs`, `erp/dev-panel`, `erp/conflict-dialog`.

## 18. Якість і приймання

### 18.1 Стрес-сторінка (приймальний тест кожної зміни основи)

Список рахунків на **10 000 рядків** з фільтрами, збереженим видом, масовим погодженням і редагуванням у комірці + картка запису. Перевіряється:
- на 360 px (телефон), 768 px (планшет у двоколонковому FCL), 1440 px (десктоп);
- українською й англійською;
- у світлій і темній темі, у Сапфірі й Графіті;
- у звичайній і компактній щільності;
- лише з клавіатури й зі скрінрідером;
- у всіх сценаріях моків (порожньо, помилка, повільно, конфлікт, без прав).

Перша задача в Claude Code — побудувати цю сторінку на Base UI + ra-core як пілот і остаточно підтвердити стек.

### 18.2 Чотири бар'єри для будь-якої нової залежності

1. **Ліцензія** — розділ 5.
2. **Підтримка** — реліз приблизно за останні 6 місяців, React 19 у peer-залежностях.
3. **Стек** — працює з Vite і токенами Tailwind v4 без другого рантайму стилів.
4. **Походження вендора** — відповідає політиці (розділ 5).

### 18.3 Двадцять критеріїв якості (оцінка 0–3, у дужках вага)

1. Шаблони ERP-сторінок (×2). 2. Глибина гріда (×3). 3. Клавіатура й ARIA гріда (×3). 4. Адаптивна таблиця (×3). 5. Адаптивна розкладка й навігація (×3). 6. Фільтри й збережені види (×2). 7. Стани завантаження (×3). 8. Порожні стани (×2). 9. Валідація й помилки (×3). 10. Сповіщення (×2). 11. Disabled, read-only, права (×2). 12. Цілісність даних: незбережені зміни, блокування, конфлікт, відкат (×3). 13. Деструктивні дії (×2). 14. Довгі й масові операції (×2). 15. Щільність (×2). 16. Робота з клавіатури (×2). 17. WCAG 2.2 AA (×3). 18. Теми й контраст (×2). 19. Локалізація uk/en (×3). 20. Робота в полі й офлайн (×1; ×3 для польових клієнтів).

Детальний опис кожного критерію: `docs/research/01-ui-foundation-research.md`, розділ «Чотири бар'єри, двадцять критеріїв».

### 18.4 Тести

- **Юніт і компоненти:** Vitest + Testing Library.
- **E2E:** Playwright на демо-застосунку зі скриншотами на 360, 768 і 1440 px, у світлій і темній темі.
- **Доступність:** axe у Playwright; ручна перевірка клавіатурою для нових компонентів.
- **Контракти:** zod-схеми валідують і відповіді моків, і реальні відповіді бекенду в інтеграційних тестах проекту.
- **Палітри:** зміна `palette-tokens.json` перезапускає перевірку контрасту; будь-яка помилка блокує злиття.

### 18.5 Швидкість: бюджети й перевірка

- **Відгук на дії (INP) ≤ 200 мс** і **перший екран (LCP) ≤ 2,5 с** на телефоні середнього класу: CPU у 4 рази повільніше за еталонний Mac (на повільнішій машині, зокрема в CI, множник калібрується еталонним навантаженням, ADR-0009), мережа 4G 9 Мбіт/с із затримкою 40 мс, холодний кеш, 390 px. Міряє Playwright (`pnpm perf`, медіана з п'яти прогонів) на стрес-сторінці (у демо — «Дані й моки», 10 000 рахунків, на 390 px — картки): відкриття, пошук, фільтр статусу, сортування, палітра команд; перевищення валить CI.
- **JS першого екрана:** ціль ≤ 250 КБ gzip. На цьому стеку вона поки недосяжна (самі бібліотеки ≈ 230–260 КБ), тому діє храповик: межа кожного маршруту демо — факт + 5 % (`apps/demo/bundle-budget.json`, `pnpm check:bundle`), зростання — лише явним оновленням меж у PR. Шар моків у бюджет не входить.
- Сторінки — окремими чанками з попереднім завантаженням при наведенні (`lib/lazy`); у пам'яті лише мова інтерфейсу; важкі частини, які показуються не одразу (палітра команд), вантажаться, коли браузер вільний, або при першому відкритті (ADR-0009).
- Чанк чи мова можуть не завантажитись (офлайн, застарілий чанк після деплою): замість білого екрана — `erp/error-boundary` зі станом помилки й повтором; мова лишається запасною українською, і інтерфейс про це каже.

## 19. Робота з Claude Code

Файли:
- `CLAUDE.md` у корені `erp-ui` — правила роботи в самому реєстрі.
- `registry/claude/CLAUDE.project.md` — блок, який додається в CLAUDE.md кожного клієнтського проекту.
- `registry/claude/skills/erp-ui/SKILL.md` — скіл, що ставиться в проект через реєстр (`npx shadcn add VasulenkoIllia/erp-ui/claude`, входить і в `base`) у `.claude/skills/erp-ui/`. Так він однаковий у всіх розробників команди.
- MCP-сервер shadcn — щоб Claude шукав і додавав компоненти з реєстру.

Обов'язкові правила для агента (повний текст — у скілі):
1. Будь-який UI — лише з компонентів і шаблонів реєстру. Немає потрібного — спершу додати в реєстр, потім використати.
2. Ніяких власних кольорів, відступів, радіусів, шрифтів: лише токени.
3. Кожен екран: усі стани з розділу 8, адаптив з розділу 9, доступність з розділу 10, рядки через i18n.
4. Дані — лише через контракт модуля; моки оновлюються разом із контрактом.
5. Нова залежність — лише після чотирьох бар'єрів (18.2).
6. Перед здачею — стрес-перевірка: 360/768/1440, світла/темна тема, uk/en, клавіатура, сценарії моків.
7. Вдалий новий компонент у проекті → запропонувати перенести в реєстр.
8. Локальні зміни компонента з реєстру → позначка `erp-ui: local override` з причиною.

Команда:
- Реєстр — приватний репозиторій у GitHub. Кожен розробник має доступ на читання й власний токен у `.env.local`.
- Зміни в реєстр — лише через PR із перевірками (тести, контраст, axe, скриншоти).
- Версіонування: теги `vX.Y.Z` + `CHANGELOG.md`; мажорна версія — лише при зміні токенів чи API компонентів.
