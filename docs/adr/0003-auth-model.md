# 0003. Модель входу й контракт профілю

- Статус: прийнято; доповнено [ADR-0010](0010-sign-in-methods.md) (способи входу, відновлення, сесія)
- Дата: 13.10.2026
- Хто ухвалив: власник (вікторина 13.10.2026)

## Контекст

PF01 (SPEC §12) — вхід, ролі й права — будується один раз для всіх проектів.
Контракти модулів мають знати:

- як передається сесія;
- як описано права;
- де лежать вподобання користувача (PF11).

У project-a уже працює cookie-сесія з 2FA.

## Рішення

1. **Сесія — httpOnly cookie + 2FA застосунком (TOTP)** (вибір власника):
   - `POST /auth/login` `{ email, password }` → `{ status: "authenticated" | "two_factor_required" }`.
     Сервер ставить cookie; для 2FA — тимчасову, що дозволяє лише крок коду.
   - `POST /auth/2fa` `{ code }` → `{ status: "authenticated" }`; хибний код — 422 з `fieldErrors.code`.
   - `POST /auth/logout` → 204.
   - Токенів у JS немає: їх не вкрасти через XSS, а сесію сервер відкликає сам.
     Cookie — `Secure`, `SameSite=Lax` або `Strict`.
2. **Профіль — `GET /me`** (без сесії — 401):
   `{ id, name, email, avatarUrl?, roles, permissions, companies, companyId, twoFactorEnabled }`.
   - `permissions` — ефективні права з усіх ролей, рядки `<ресурс>:<дія>`;
     `<ресурс>:*` і `*` — будь-яка дія.
   - Дії ra-core зводяться до прав erp-ui: `list`/`show`/`export` → `read`, `edit` → `update`.
   - `companies` — доступні компанії (PF02); `companyId` — за замовчуванням для `X-Company-Id`.
3. **Права на клієнті лише ховають і вимикають дії** (SPEC §8.4: неактивна кнопка у фокусі з причиною).
   Сервер і моки перевіряють ті самі права самі й відповідають 403.
4. **401 завершує сесію, 403 — ні:**
   - `checkError` виходить лише на 401;
   - 403 — це «немає прав на цю дію» і показується станом `forbidden`.
5. **Вподобання — `GET`/`PUT /me/preferences`** (PF11): `{ palette, theme, density, sidebar, language }`.
   - Сервер — джерело правди; localStorage — лише кеш, щоб не блимало до відповіді.
   - `syncPreferences` після входу застосовує серверні значення, далі зберігає кожну зміну з паузою 0,5 с.
   - Збережені види таблиць додадуться до цього контракту з PF04/PF05.
6. **Реалізація в кіті:**
   - `lib/auth`:
     - схеми;
     - `createAuthProvider` — authProvider ra-core з `getMe`;
     - `hasPermission`;
     - `ME_QUERY_KEY`.
   - `hooks/use-me`:
     - профіль із кешу TanStack Query; `null` — гість;
     - кеш оновлює `onMe` провайдера.
   - `lib/preferences` — `syncPreferences`.
   - `lib/mocks` — `createPlatformHandlers` з входом, 2FA, `/me` і вподобаннями.

## Наслідки

- Демо показує повний цикл:
  - гість → `/login` → код 2FA → повернення на сторінку;
  - вихід;
  - менеджер без права редагування;
  - вподобання, що повертаються на чистому браузері.
- Компанію за замовчуванням застосунок обирає під час завантаження профілю, до перших запитів даних.
- Ролі й редактор прав (A2) — модуль хвилі 1; формат прав уже фіксований.
- SSO/OIDC, якщо знадобиться клієнту, — окремий ADR. `logout` може повернути адресу перенаправлення.

## Розглянуті варіанти

- **JWT у localStorage + refresh-токен** — вразливо до XSS, складніше відкликати; потрібне лише для мобільних клієнтів, яких у хвилях немає.
- **Права як ролі на клієнті** («бухгалтер може…») — кожен проект дублював би матрицю; ефективні права з сервера простіші й безпечніші.
- **Вподобання лише в localStorage** — не переносяться між пристроями; SPEC §6.2 вимагає зберігати на сервері.
