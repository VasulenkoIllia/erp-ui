# 0092. Стеля першого екрана й API платформи, що вантажаться при першому виклику

- Статус: прийнято (змінює ADR-0009; доповнює ADR-0021)
- Дата: 15.11.2026
- Хто ухвалив: власник, 15.11.2026 (рекомендовані варіанти: стеля — вага входу після цього кроку, до рівня v1.3.0 —
  окремим кроком із рядками функцій; API платформи ліниві на тому самому місці; у звіті три числа входу, валить лише
  стеля)

## Контекст

- ADR-0009 ввів храповик «факт + 5 %» із ціллю 250 КБ gzip. На практиці межу входу піднімали майже кожним кроком на
  кілька десятих: з 400,2 КБ у v1.3.0 до 412,1 КБ, і жодного разу не знизили. Запас лишався 0,1 КБ, а не 5 %, правка
  меж стала звичайною частиною PR, і ніде не було видно, хто й навіщо додав вагу. Ціль 250 КБ на цьому стеку недосяжна:
  самі бібліотеки у вході важать близько 297 КБ.
- Межа кожної сторінки містила вхід, тож будь-який ріст входу піднімав усі 80+ меж разом.
- `lib/auth` складав усі API платформи (акаунт, безпека, аудит, вебхуки, ролі, запрошення, сповіщення, канал подій,
  стрічка, компанія) статичними імпортами. Їхні контракти зі схемами лежали в першому екрані, хоч оболонка на старті
  більшості з них не викликає, і кожен новий API (кошик, погодження, пошта) додав би туди ще.
- `localizedText` жив у `lib/auth`: компонент, якому потрібен лише переклад рядка (`erp/status-badge` через
  `lib/statuses`), тягнув за собою `lib/auth`, ra-core і всі API, 67 файлів у реєстрі.

## Рішення

1. **Стеля входу.** `entryCeilingKb` у `apps/demo/bundle-budget.json`: вхід вище неї валить CI (`pnpm check:bundle`).
   Підняти стелю можна лише ADR із причиною; `--update` її не змінює. Перше значення — вага входу після цього рішення
   плюс 0,1: 404,8 КБ. Напрям — рівень v1.3.0 (400,2 КБ): рядки функцій вантажаться разом із функцією, а не на старті;
   далі близько 350 КБ за рахунок інших резервів (іконки модулів, таблиці класів, дрібні чанки). Ціль 250 КБ знято.
2. **Сторінка — власна частина.** Межа сторінки стоїть на тому, що вона додає до входу: її чанк зі статичними
   імпортами без вхідного. Це храповик: `--update` пише факт + 0,1 КБ, ріст видно в диффі PR. Ріст входу межі сторінок
   не зачіпає, за нього відповідає стеля. Звіт показує й увесь перший екран маршруту.
3. **Склад входу у звіті:** бібліотеки, кіт і демо окремими числами. Це оцінка: плагін збірки демо (`bundleSources` в
   `apps/demo/vite.config.ts`) пише gzip коду кожної групи в чанку, скрипт зводить ці числа до справжнього розміру
   чанка. Окремої межі на код кіта немає: валить лише стеля.
4. **Шар моків має свою межу**, храповик, як у сторінок. У збірці проекту з бекендом моків немає (ADR-0079), але в
   демо шар росте з кожним модулем.
5. **API платформи — `lib/platform-api`.** `createPlatformApis(client)` складає API, `createAuthProvider` бере їх
   звідти, а `ErpAuthProvider` розширює `PlatformApis`: поля, типи й доступ `authProvider.audit` ті самі. Акаунт,
   безпека, аудит, вебхуки, запрошення й стрічка ліниві (`lazyApi`): їхній код вантажиться окремим чанком при першому
   виклику будь-якого методу. Методи — власні поля об'єкта, тож перевизначення в адаптері
   (`{ ...kitAuth.admin, blockUser }`, ADR-0021) працює як раніше. Одразу створюється те, що оболонка використовує до
   першої дії людини: сповіщення, канал подій, компанія й ролі (перевірка прав).
6. **Чанк, що не завантажився** (офлайн, застарілий деплой), відхиляє виклик помилкою браузера, яку розпізнає
   `isChunkLoadError` (ADR-0055). Запит даних повторюється раз, як після збою мережі (`lib/query-client`); текст помилки
   (`useApiErrorMessage`, рядок `apiErrors.chunk_load`) просить оновити сторінку, бо після деплою старого чанка вже немає.
   Наступний виклик пробує завантажити чанк знову. Компоненти кіта, що читають ці API запитами, імпортують з файла API
   ключі запитів і схеми, тож його чанк приходить разом із ними; збій першого виклику можливий там, де код лише
   викликає метод (дії форм, діалоги, код проекту).
7. **Новий API платформи** додається в `lib/platform-api` лінивим, через `lazyApi` з переліком методів: TypeScript не
   дасть пропустити метод чи лишити зайвий. У перший екран іде лише те, що потрібне оболонці на старті. Окремий об'єкт
   API платформи поруч із провайдером входу — лише з мажорною версією, якщо знадобиться. `lazyApi` годиться й для свого
   API проекту, якого перший екран не потребує.
8. **Листові файли.** `localizedText`, `localizedTextSchema` і `LocalizedText` — у `lib/localized-text`; `AUTH_FACTORS`
   і `SETUP_FACTORS` — у `lib/auth-factors`. Вони не залежать від інших файлів кіта. `lib/auth` і `lib/account`
   реекспортують старі імена; вилучити їх можна лише з мажорною версією.

## Наслідки

- Вхід демо: 412,0 → 404,7 КБ gzip. Чанки аудиту, стрічки, дат і форматованого тексту пішли з першого екрана; сторінки,
  яким вони потрібні, вантажать їх разом із собою.
- Замикання `erp/status-badge` у реєстрі — 44 файли замість 67, без ra-core.
- PR, що додає вагу у вхід, мусить спершу зняти її або принести ADR. Найближчий ризик — нові рядки в `lib/i18n-uk`:
  поки рядки функцій лежать у першому екрані, кожна нова функція додає туди свої.
- Версія мінорна: нові файли й функції, публічні імена й тип `ErpAuthProvider` ті самі. Проекту нічого міняти не треба.
  Видно дві дрібниці: метод лінивого API — обгортка, тож тест із `toBe(createAuditApi(…).getEvents)` треба переписати на
  результат виклику; новий рядок кіта `apiErrors.chunk_load`.
- Перший виклик лінивого API — ще один невеликий запит чанка, якщо сторінка не завантажила його сама.

## Розглянуті варіанти

- **Стеля одразу 400,2 КБ:** у тому самому кроці ще й перенести рядки функцій з першого екрана. Крок помітно більший;
  обрано окремий крок.
- **Стеля на 412,1 КБ:** без кроку повернення вхід лишався б вищим, ніж у v1.3.0.
- **Окремий об'єкт `platform` поруч з `authProvider` уже зараз:** кожен проект додавав би його в корінь застосунку.
- **Окрема межа на код кіта у вході:** ще одне число, яке треба підтримувати; склад і так видно у звіті.
