# 0031. Модуль A2 «Користувачі й ролі»: список і картка людини, довідник `users`, спільні помічники сторінок модулів

- Статус: прийнято (доповнює ADR-0013, ADR-0014, ADR-0020, ADR-0025 і ADR-0030)
- Дата: 26.10.2026
- Хто ухвалив: власник (вікторина на старті A2b, `docs/WAVE-1.md`, «A2»)

## Контекст

Крок A2b — модуль `modules/A2-users` за правилом 2 CLAUDE.md: список користувачів, картка з
вкладками «Доступ», «Ролі», «Сесії», «Історія», ролі й матриця прав, запрошення. Платформа вже
вміє доступ людини (ADR-0013), ролі й запрошення (ADR-0014), але лише панелями демо, без модуля:
немає ресурсу людей компанії зі списком, фільтрами й карткою.

З A2a лишились два питання до контракту `users`: поле-запис «Відповідальний менеджер» у B1 показує
«Немає доступу» в кожному рядку тому, хто не має `users:read`, а журнал не може назвати людину, яку
читач не бачить (ADR-0030, «Наслідки»). Обидва вирішує політика читання довідника людей.

Ще дві перешкоди в коді: `erp/user-access` мав 835 рядків (межа — 800), а помічники сторінок B1
(`use-extended-list`, `use-card-record`, `use-page-heading`, `use-history-refresh`, посилання зі
списку) жили в теці модуля B1, і A2 мусив би їх скопіювати.

Вікторина на старті A2b (26.10.2026, усі відповіді — рекомендовані):
- A2b — двома PR: **A2b1** — список і картка людини, контракт `users`, довідник для полів-записів;
  **A2b2** — сторінки ролей і запрошень у модулі, перевірка запрошення `POST` з токеном у тілі;
- довідник `users`: ім'я та email колег бачить кожен у компанії; ролі, входи й блокування — лише з
  `users:read`;
- помічники B1 — у спільний шар, копії з B1 видалити.

## Рішення

1. **Контракт `users`** (`registry/modules/A2-users/contract.ts`, ADR-0002):
   - `GET /users` (`{ data, total }`) і `GET /users/:id` — люди компанії з `X-Company-Id`:
     ```ts
     { id, version, name, email, position, status: "active" | "blocked",
       roles: { id, name }[],          // назва ролі — мовою Accept-Language
       twoFactor: boolean, lastSignInAt: string | null, …поля розширення }
     ```
   - фільтри — `q` (ім'я, email), `status`, `roles=<id ролі>` («одне з»), `twoFactor=true|false`,
     `id=a&id=b`, поля розширення; сортування — `name`, `email`, `lastSignInAt`;
   - ресурс лише для читання: ролі змінює `PUT /users/:id/roles`, блокування — `POST
     /users/:id/block` і `/unblock`, вихід — `POST /users/:id/sign-out`, другий крок — наявні
     ендпоінти доступу (ADR-0013, ADR-0014). Після них `version` запису зростає — картка
     перечитує «Історію» (`hooks/use-history-refresh`, ADR-0028);
   - компанію визначає сервер: `X-Company-Id`, без нього — активна компанія сесії; компанія, де
     людина не працює, — 403, права — у компанії запиту (`mockRequestCompany` з `lib/mock-server`,
     той самий, що в `lib/mock-company`); людина іншої компанії — 404, без сесії — 401.
2. **Довідник без `users:read`** — короткий запис `{ id, version, name, email }`
   (`userDirectoryEntrySchema`):
   - пошук `q` і сторінки — лише активні люди; за `id` — будь-хто з компанії, щоб підпис уже
     вибраного (зокрема заблокованого) не став «Немає доступу»;
   - будь-який інший фільтр і сортування не за `name`, `email` чи `id` — 403 `forbidden`: інакше
     `total` за `status=blocked` чи порядок за `lastSignInAt` розкрили б те, що бачить лише
     `users:read`;
   - що довідник усе ж показує (свідомо): людина, знайдена за `id`, але не в пошуку, —
     деактивована; `version` зростає й зі зміною ролей чи блокуванням. Бекенд обмежує `perPage`
     довідника й частоту запитів;
   - так поле-запис на `users` у будь-якому модулі показує імена всім у компанії, а журнал моків —
     назву людини (`registerMockRecords`). «Немає доступу» лишається для довідників, які роль не
     читає.
3. **Модуль `modules/A2-users`** (ADR-0025): фабрика `createUsersModule({ basePath?, extension?,
   homePath? })` → `{ id: "A2", paths, routes, nav, resources, preload }`; `homePath` — куди
   перейти після «Увійти як…». Сторінки — лінивими чанками:
   - список — `templates/list-report`: вкладки «Усі» і статуси з лічильниками, фільтри «Роль»
     (назви — з каталогу ролей, якщо є `roles:read`) і «Другий крок», пошук, сторінки сервера;
   - картка — `templates/object-page-tabs`: шапка зі статусом, «Це ви» на своїй картці, поля
     (email, посада, ролі, останній вхід) і дія «Увійти як…» (з `users:impersonate`, не для себе й
     не під час «Увійти як…»; без права — неактивна з причиною, SPEC §8.4); вкладки «Доступ» і
     «Сесії» — з `users:update`, «Ролі» — зміна з `users:update` і `roles:read`, інакше лише
     перегляд; «Історія» — бічна колонка з `audit:read`, на телефоні — остання вкладка; під час
     «Увійти як…» вкладок змін немає, ролі — лише назвами з причиною (сервер однаково відмовить,
     ADR-0011); запис із кешу, який не вдалося перечитати, — стан помилки з повтором над
     вкладками; своя картка — без дій над
     собою (свій доступ — у налаштуваннях безпеки);
   - без `users:read` — «Немає доступу» на місці списку й картки (`PageState`), а не порожній
     список;
   - ресурси для прав і моків: `users` (`read`, `create`, `update`, `impersonate`), `roles`
     (`read`, `update`).
4. **Тип розширення** `UsersExtension` (ADR-0020) — зміни згруповано за сутністю `users`:
   ```ts
   interface UsersExtension {
     users?: { fields?, columns?, filters?, tabs?, recordFields?, history?: boolean,
               sections?, actions? }
     strings?: { uk?, en? }
   }
   // ключі модуля: UserColumnId, UserFilterId, UserTabId, UserFieldId, UserSectionId, UserActionId
   ```
   Форми немає: людину створює запрошення, ролі й доступ змінюють вкладки картки. Ролі й
   запрошення (A2b2) і права на рівні записів (A2c) з'являться новими необов'язковими ключами
   поруч з `users` — наявні файли розширення не ламаються (доповнення, мінорна версія).
5. **Моки** (`mocks.ts`, `fixtures.ts`): ресурс `users` — живий вигляд користувачів мок-сервера
   входу (профіль, ролі `lib/mock-team`, другий крок, останній вхід і блокування
   `lib/mock-account`), а не окрема таблиця, тож панелі доступу, ролей і журнал бачать ті самі дані;
   сценарії ресурсу — `success`, `error`, `empty`, `slow`, `forbidden`, `offline` (`conflict`
   модуля не стосується: запис він не змінює). Фікстури — 16 колег українською й англійською
   (`createUsersFixtures({ company, roles, emailDomain })`) для `createPlatformHandlers({ users,
   accountSeeds })`: ролі по черзі, кожен третій з другим кроком, кожен сьомий ще не входив, двоє
   заблоковані; пароль — випадковий, колеги не входять у демо.
6. **Спільний шар** замість копій:
   - `hooks/use-extended-list`, `hooks/use-card-record`, `hooks/use-page-heading`,
     `hooks/use-history-refresh`, `hooks/use-tab-param` (вкладка картки в адресі) і
     `erp/record-link` (`RecordLink`, `BackToList`) — з B1 без зміни поведінки, копії з B1 видалено;
   - `moduleResources(uk, loadEn)` у `lib/i18n-namespaces` — рядки модуля з перевизначеннями
     розширення, англійські — окремим чанком, один набір на об'єкт `strings`;
   - `lib/mocks`: `filterMockRecords` і `sortMockRecords` (пошук, плоскі фільтри й сортування
     `createResourceHandlers` для моків, що будують записи самі), `registerMockRecords` (назва
     запису в журналі моків для ресурсу без `createResourceHandlers`);
   - `MockAccountSeed.blocked` — заблокований акаунт у початковому стані.
7. **`erp/user-access` розділено без зміни поведінки** (окремий коміт, ті самі тести): дані
   доступу `erp/user-access-data`, дії й діалоги `erp/user-access-actions`, ролі людини
   `erp/user-roles-section`, сесії `erp/user-sessions`; панель доступу (`useUserAccessSheet`) —
   194 рядки. Картка модуля бере ті самі частини, тож поведінка панелі й вкладок однакова; стани
   запиту доступу — один `UserAccessQuery`. Після будь-якої дії доступу (вихід, завершена сесія,
   скинутий другий крок, блокування, ролі) `useRefreshAccess` перечитує й журнал: подія одразу в
   «Історії», хоча версія запису змінюється лише від ролей і блокування.
8. **Демо**: модуль на місці заглушки `/m/A2` з розширенням `src/extensions/A2-users.ts` (поле
   «Відділ», вкладка «Без другого кроку», інша назва колонки «Посада»); модулі кіта в демо —
   `kit-modules.ts` (маршрути, навігація, `preload`); власний ресурс `users` демо замінено моками
   модуля.

## Наслідки

- Бекенд, що ставить A2, віддає людей компанії за контрактом вище й сам виконує політику
  довідника. pilot-api списку людей не має: адаптер тестового проекту чи рішення не ставити A2
  на цей бекенд — у A2c.
- Поле-запис на `users` у B1 і будь-якому модулі тепер показує імена тим, хто не має
  `users:read`: це рішення власника, а не витік — ім'я та email колег і так видно в листах,
  згадках і журналі.
- Файли B1 змінились (імпорти помічників зі спільного шару); у проекті оновлення модуля B1 бере
  нові файли `hooks/…` і `erp/record-link` залежностями елемента. Команда оновлення кіта файлів,
  яких у кіті більше немає, не видаляє, а називає (`? шлях`, `docs/using-erp-ui.md`, розділ 8):
  п'ять старих файлів B1 лишаться в проекті невживаними, доки їх не видалити руками (тестовий
  проект — у A2c).
- Публічний API кіта — лише доповнення (мінорна версія з A2c): нові елементи, експорти `lib/mocks`
  і `lib/i18n-namespaces`, необов'язкове поле `MockAccountSeed.blocked`; тип розширення B1 не
  змінився.
- Демо: у компанії бухгалтерки 19 людей замість 3, тож e2e, що рахували людей чи шукали
  «Заблоковано» в списку, уточнено (`team.spec`, `operations.spec`, `record-field.spec`).
- Скасування повторного підтвердження під час збереження ролей показує «Не вдалося увійти: …»
  (текст екранів входу) — так було й у панелі доступу до розділу; формулювання — окремим
  кроком, не в A2b1.

## Розглянуті варіанти

- **Довідник лише з `users:read`** (як у демо A2a): поле-запис на `users` показує «Немає доступу»
  в кожному рядку менеджеру без права, журнал — `id`. Відхилено вікториною: ім'я колеги — не
  таємниця в компанії.
- **Окремий ресурс `/users/directory`** для довідника: поле-запис бере один ресурс за назвою, а два
  ресурси для однієї сутності — два кеші й два набори прав. Відхилено: одна адреса, відповідь за
  правом.
- **Фільтри для довідника без права з тихим ігноруванням** замість 403: клієнт отримав би список,
  який не відповідає запиту, і не дізнався б чому. Відхилено.
- **Окрема таблиця людей у моках модуля** (як `createResourceHandlers`): ролі, блокування й вхід
  розійшлися б із панелями доступу й журналом. Відхилено: живий вигляд даних мок-сервера.
- **Копії помічників B1 у A2**: два місця для одного виправлення. Відхилено власником.
- **Розширити `erp/user-access` понад 800 рядків**: порушує межу розміру файлів. Відхилено:
  спершу розділ без зміни поведінки.
