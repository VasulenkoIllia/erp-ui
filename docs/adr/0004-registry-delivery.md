# 0004. Реєстр: структура, назви, доставка й оновлення в проектах

- Статус: прийнято
- Дата: 13.10.2026
- Хто ухвалив: власник (крок 0.2b)

## Контекст

SPEC §3.3 передбачав `npx shadcn add @erp-ui/<item>` з приватного GitHub-реєстру з токеном у `.env.local`. З серпня 2026 shadcn CLI сам читає **приватні GitHub-репозиторії як реєстри-джерела**: досить `registry.json` у корені, без збірки й без сервера; доступ — через `gh` або `GH_TOKEN`.

Перевірено в кроці 0.2b на реальному репозиторії:
- `add` з коміту чи тегу (`#ref`) працює для приватного репозиторію;
- CLI переписує імпорти `@/registry/…` на аліаси проекту з його `components.json`;
- `registryDependencies` **не успадковують ref**: залежність без `#ref` береться з гілки за замовчуванням, тобто версії змішуються;
- коментар у першому рядку файла CLI вирізає;
- `add --diff` показує по кожному файлу, що зміниться.

## Рішення

1. **Адреса:** `VasulenkoIllia/erp-ui/<елемент>[#ref]`. Простір імен `@erp-ui` не використовуємо: для нього потрібні зібрані JSON і власний хостинг, а GitHub-адреса дає версії через теги без інфраструктури.
2. **Назви елементів** — `<шар>/<назва>`: `ui/button`, `lib/utils`, `hooks/use-resolved-theme`; збірні — `base`, `tokens`, `claude`. Шари `erp/…`, `templates/…`, `modules/<ID>-<назва>` — так само, коли з'являться.
3. **Кожен елемент несе всі свої файли** (замикання імпортів `@/registry/…`) замість `registryDependencies`. Одна команда з `#vX.Y.Z` ставить узгоджений набір з однієї версії; імпорти переписуються правильно.
4. **`registry.json` генерується** (`pnpm registry`) з коду `registry/` і опису `registry/registry.config.mjs`: npm-залежності — з імпортів (версії з `registry/package.json`), метадані каталогу — у `meta` (шар, статус, сторінка демо, SPEC). `pnpm lint` перевіряє, що `registry.json` і `docs/CATALOG.md` актуальні, схема shadcn проходить, сторінки демо існують, а дві копії скіла не розійшлися.
5. **Куди лягає в проекті** (за `components.json` проекту): `ui/*` → `src/components/ui/`, `lib/*` → `src/lib/`, `hooks/*` → `src/hooks/`; стилі — `src/styles/erp-ui/`; `base` замінює `src/index.css` точкою входу erp-ui; скіл — `.claude/skills/erp-ui/`; SPEC, каталог і блок для CLAUDE.md — `docs/erp-ui/`.
6. **Шапка походження** — одразу після імпортів (не в першому рядку).
7. **Версії** — git-теги `vX.Y.Z` (CLAUDE.md, правило 8). Проект закріплює версію через `#vX.Y.Z`; без ref береться `main`, а він завжди зелений, бо мерджимо лише з зеленим CI.
8. **Оновлення в проекті:** `add … --diff` → переглянути → `add …` → прогнати перевірки. Локальні правки позначені `// erp-ui: local override — <причина>`, їх видно в диффі.
9. **Доступ:** розробник — `gh auth login`; CI проекту — fine-grained токен із правом **Contents: Read-only** на `erp-ui` у `GH_TOKEN`. З 31.10.2026 репозиторій відкритий, `shadcn add` токена не потребує (ADR-0048).
10. **Перевірка доставки в CI** (`pnpm consumer-smoke`): на кожен PR чистий Vite-проект робить `shadcn init` (Nova) і `add base` + усі `ui/*` з коміту PR, потім `tsc` і `vite build`.

## Наслідки

- Нові компоненти мусять мати запис у `registry/registry.config.mjs`, інакше `pnpm lint` упаде: каталог завжди повний.
- Встановлення `ui/dialog` перезаписує й `ui/button` та `lib/utils` тієї ж версії. Якщо в проекті є локальна правка, CLI спитає, чи перезаписувати; правка видна в `--diff`.
- SPEC §3.3 і блок CLAUDE.md для проектів оновлено під GitHub-адресу.

## Доповнення: крок 1.9 — оновлення однією командою (20.10.2026)

П. 8 замінює команда кіта в проекті (ADR-0029): `node scripts/erp-ui-kit.mjs update vX.Y.Z` —
архів тегу одним запитом, `shadcn build`, звіт `add --dry-run`, `add --overwrite --yes` усіх
встановлених елементів (список — у `kit-files.json`), закріплена версія CLI, відбитки файлів кіта;
`--dry-run` — лише звіт, `check` — файли кіта не правлені. Команду ставить `base` (і елемент
`tools/kit`). Новий шар `tools` — «Інструменти проекту»: файли, що лягають у `scripts/` і `e2e/`
проекту, а не в `src/`. `base` і `tokens` більше не оголошують залежність `shadcn`.
