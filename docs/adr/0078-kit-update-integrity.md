# 0078. Оновлення кіта: SHA й відбиток реєстру, той самий тег з іншим умістом, контрольна сума маніфесту, сироти

- Статус: прийнято (доповнює ADR-0029 і ADR-0076)
- Дата: 11.11.2026
- Хто ухвалив: власник, 11.11.2026 (рекомендований варіант: усе разом)

## Контекст

Команда кіта (ADR-0029) брала версію за назвою тегу й не записувала, який це коміт. Тег, перестворений на іншому коміті
(помилка випуску, переписана історія, хтось із правом запису), давав проекту інший код під тією ж версією: `update v1.3.0`
з іншим умістом змінював файли без попередження, а гілка з GitHub записувалась у маніфест без SHA. Репозиторій
відкритий (ADR-0048), а оновлення доставляє також скіл і блок інструкцій агента.

`kit-files.json` не мав захисту від правки руками: якщо з нього зникав елемент разом із відбитками, `check` лишався
зеленим, а модуль тихо переставав оновлюватись. Файл, якого в новій версії немає (сирота), лишався в проекті й зникав із
маніфесту, а рядок про нього стояв посеред довгого звіту.

Файл кіта без відбитка в маніфесті (перший `update --items` чи загублений маніфест) `update` перезаписував без
попередження, навіть із позначкою локальної правки старого правила (ADR-0076 п. 3).

## Рішення

1. **Версія в маніфесті:** `kit` (тег; для гілки — гілка з SHA), `sha` (коміт) і `fingerprint` (відбиток реєстру:
   sha256 від `registry.json` і всіх файлів, на які він посилається, за шляхами; не залежить від git і версії CLI).
   З GitHub (`--hostname github.com`) команда спершу бере SHA коміту тегу (`commits/refs/tags/<тег>`: саме тег, не
   гілка з тією самою назвою), потім архів саме цього коміту. У відбиток ідуть лише звичайні файли всередині архіву:
   символьне посилання (на ключі, токени, пристрій) зупиняє оновлення. Залежності елементів — лише з цього реєстру.
2. **Той самий тег з іншим SHA:** відбиток інший — зупинка до запису «та сама версія, інший вміст»; відбиток той самий
   (історію переписали, вміст не змінився) — попередження й новий SHA в маніфесті. `--dry-run` попереджає. SHA минулого
   встановлення не записано (його ставила попередня версія команди) — звірити нема з чим: попередження й SHA, який команда
   записує, щоб людина звірила його з `CHANGELOG.md` на `main`. Тож захист діє з другого оновлення новою командою; перше
   радимо робити нею ж із тимчасової теки, як з v1.0.0 на v1.0.1.
3. **Контрольна сума маніфесту** (`checksum`): sha256 усіх полів, крім неї самої, без ключа. Це захист від випадкової
   правки (зник елемент, конфлікт злиття), а не від підробки: перерахувати суму може будь-хто. `check` зупиняється, якщо
   сума не збігається чи її немає поруч із полями нової команди (`sha`, `fingerprint`, `orphans`); навмисну зміну
   (елемент прибрали зі списку `items`) записує наступний `update`, він попереджає. Маніфест попередньої версії команди
   без суми `check` приймає з нагадуванням. Шляхи в маніфесті — лише відносні шляхи проекту (без `..`, `.git/`,
   `node_modules/`), відбитки — sha256.
4. **Сироти** (`orphans`: шлях → відбиток версії кіта): файли, яких у новій версії немає, а в проекті вони є. `update`
   називає їх наприкінці звіту й пам'ятає між оновленнями, `check` про них попереджає (код 0). `--prune` видаляє сироти,
   яких проект не змінював, і лише звичайні файли всередині проекту, які відстежує git (їх повертає `git restore`; не
   символьні посилання, не теки, не ігноровані); решта лишаються сиротами. `--dry-run --prune` показує, що видалиться.
   Шлях, що в новій версії лише змінив регістр, — не сирота. Змінену в проекті сироту, яку нова версія повертає, `update`
   не перезаписує, а зупиняється.
5. **Позначка локальної правки старого правила:** перед записом `update` шукає її в коментарях коду (`//`, `/*` чи рядок `*`
   блокового коментаря, далі `erp-ui: local override`) у файлах, які перезапише, і зупиняється зі списком; markdown не
   перевіряє.
6. **Теги `v*` не пересувають і не видаляють:** правило тегів GitHub (оновлення, вилучення й force push заборонені,
   обхідників немає) — налаштування репозиторію, робить власник. Створення не обмежене: тег ставить workflow випуску.
   Помилку випуску виправляє нова патч-версія, а не перестворений тег.
7. **SHA випуску — у `CHANGELOG.md`**, рядком «Коміт тегу» під заголовком розділу версії: дописуємо першою зміною після
   тегу. Проект звіряє `sha` свого маніфесту з `CHANGELOG.md` на `main` у GitHub, а не з копією в архіві.

## Наслідки

- Пересунутий тег чи ручна правка маніфесту видно до запису й у `check`, а не після.
- Команда робить два запити до GitHub замість одного.
- Перший `update` новою командою записує новий формат маніфесту; старий маніфест читається. Оновлення, яке доставляє
  нову команду, робить ще стара: SHA вона не звіряє й не записує (довіра при першому встановленні).
- Новий тег `v*` на довільному коміті може створити кожен із правом запису: це видно лише при ручному оновленні до нього.
- Версії: мінорна (нові поля маніфесту й опція `--prune`, старий маніфест читається).

## Розглянуті варіанти

- **Підписані теги чи атестації збірки:** сильніше за SHA в маніфесті, але потребує ключів і перевірки підпису в кожному
  проекті; SHA, відбиток і правило тегів закривають основний сценарій (перестворений тег) дешевше.
- **Контрольна сума лише `items` і `files`:** простіше пояснити «будь-яка ручна правка маніфесту», ніж перелік полів.
- **`update` зупиняється на зміненому маніфесті:** тоді навмисне вилучення елемента потребувало б окремої опції; `check` у
  `lint` уже робить зміну видимою.
- **Лише SHA й тег зараз, решту пізніше:** власник вибрав усе разом.
