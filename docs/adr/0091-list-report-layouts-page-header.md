# 0091. List Report: подання списку (таблиця, дошка, календар) і шапка сторінки окремим елементом

- Статус: прийнято (доповнює ADR-0022)
- Дата: 14.11.2026
- Хто ухвалив: власник, 14.11.2026 (рекомендовані варіанти: перемикач подань у шаблоні; шапка сторінки — окремий
  елемент `erp/page-header`)

## Контекст

- Шаблон List Report (ADR-0022) показував записи лише таблицею. `mode` вибирав, як таблиця вантажить рядки, `toolbar`
  давав місце для кнопок біля фільтрів, а сам вміст був зашитий. Канбану (UI07), календарю (UI08) і модулям угод і задач
  потрібні ті самі записи дошкою чи календарем — з тими самими вкладками, фільтрами, збереженими видами й вибором. Без
  місця для вмісту кожна дошка збирала б вкладки, панель фільтрів і види наново, а вибір «таблицею чи дошкою» не
  зберігався б у збереженому виді.
- Шапку сторінки (`ListReportHeader`) брали з шаблону списку й сторінки, де списку немає: форма документа
  (`templates/document-form-page`), налаштування, ролі, «Мої справи», журнал, довідники. Разом із шапкою вони статично
  тягнули шаблон списку, а через нього — таблицю й панель фільтрів, і кожен новий шаблон повторив би цей імпорт.

## Рішення

1. **Подання (`layouts`) у `useListReport`.** Список подань із ключами `{ id, label, icon?, render? }`, як вкладки й
   фільтри: стабільний між рендерами, порядок — порядок перемикача, перше — за замовчуванням. Подання без `render` —
   таблиця шаблону; з `render` — вміст модуля замість таблиці. `render` отримує `ListReportContentProps`: ресурс, назву
   для скрінрідера (`tableLabel`), фільтр запиту (вкладка поверх панелі й `fixedFilter`), сортування з `onSortChange`,
   `isFiltered`, `onResetFilters` і вибір записів. Вміст — окремий компонент із ключем подання: хуки одного подання не
   змішуються з іншим. Поки не застосовано вид за замовчуванням, замість вмісту — скелетон, як для таблиці. Без
   `layouts` шаблон такий, як був.
2. **Перемикач у шаблоні** (`templates/list-report-layouts`). Кнопки з `aria-pressed` у групі «Подання списку» стоять
   біля «Фільтри»: після меню видів, перед `toolbar`. З одним поданням перемикача немає. Іконки подань — у словнику
   `lib/icons` (`LAYOUT_ICONS`: таблиця, картки, дошка, календар). `mode` (`scroll` чи `pages`) стосується лише таблиці.
3. **Подання — частина стану списку.** `ListState.layout`, ключі подань у `ListDefaults.layouts` (їх ставить
   `useListReport`), параметр адреси `layout`: подання за замовчуванням в адресу не пишеться, невідоме — перше. Інше
   подання — новий запис в історії, як вкладка (`setLayout`). Збережений вид зберігає подання тим самим рядком
   параметрів; подання, інше ніж у виді, — «змінено». «Стандартний» вид і «Скинути фільтри» подання не міняють: вони про
   фільтри, а не про те, як показано записи. На «нічого не знайдено» (`isFiltered`) подання не впливає. Без подань ключ
   `layout` лишається звичайним полем фільтра, тож наявні списки не змінюються.
4. **Шапка — елемент `erp/page-header`.** `PageHeader` (h1, пояснення, дії списком із ключами, `headingRef` для фокуса
   після переходу) — одна шапка для будь-якого екрана. `ListReport` із `title` ставить її сам; сторінки кіта без списку
   й форма документа беруть її напряму. `ListReportHeader` і `ListReportHeaderProps` лишаються в шаблоні псевдонімами,
   `ListReportAction` — псевдонім `PageHeaderAction`; вилучення старих імен — лише з мажорною версією. `data-slot`
   шапки — `page-header` (був `list-report-header`).
5. **SPEC §7.** List Report: шапка — `erp/page-header`, ті самі записи таблицею, дошкою чи календарем. Board: дошка
   списку сутностей — подання List Report із його вкладками, фільтрами й видами. Рядок «Print» описує сторінку друку
   документа, яка вже є в модулях (аркуш `erp/print-preview`, `erp/print-button`, ADR-0062), — екрани модулів
   збираються лише з шаблонів §7.

## Наслідки

- Шаблон дошки й календар стають поданнями списку: вкладки, фільтри, види, вибір і лічильники вкладок — від List
  Report. Вміст подання сам вантажить записи за отриманим фільтром і показує стани колекції (SPEC §8.1). Зразок —
  подання «Картки» на сторінці «Організації» демо.
- Сторінки, що брали лише шапку, більше не тягнуть таблицю; замикання їхніх модулів у реєстрі менше: шаблон списку,
  таблиця та їхні залежності приходять лише з модулями, що мають списки.
- Проект, у якому шаблон списку стояв лише як залежність модуля, що тепер бере тільки шапку, після оновлення побачить
  його файли сиротами; якщо свої сторінки проекту їх імпортують, шаблон ставлять явно (`--add templates/list-report`)
  до `--prune`.
- Версія: нові елементи, необов'язкові поля й поведінка списків без `layouts` та сама — мінорна. Нові поля в типах, які
  заповнює кіт (`ListStateApi.setLayout`, `ListReportState.layouts`), — мінорна за правилом SPEC §19.
- У списку з поданнями поле фільтра не можна назвати `layout`.

## Розглянуті варіанти

- **Лише місце для вмісту, перемикач — у модулі** (через `toolbar`): менше в шаблоні, але угоди, задачі й календар
  повторили б той самий перемикач, а запам'ятовування подання в адресі й виді кожен робив би сам.
- **Окремий шаблон дошки зі своїми вкладками й фільтрами:** дублює List Report і розводить збережені види списку й
  дошки одного ресурсу.
- **Подання поза станом списку** (стан сторінки чи особисте налаштування): не зберігається у виді й не відкривається
  посиланням.
- **Шапка окремим файлом усередині шаблону списку:** без нового імені, але форма документа й налаштування й далі
  формально залежали б від шаблону списку.
