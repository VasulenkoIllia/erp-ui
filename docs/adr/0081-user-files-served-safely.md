# 0081. Файли користувачів: сервер віддає їх так, щоб вони не виконувались у застосунку

- Статус: прийнято (доповнює ADR-0014 і ADR-0053)
- Дата: 12.11.2026
- Хто ухвалив: власник, 12.11.2026 (рекомендований варіант: вимога до сервера, код кіта не змінюється)

## Контекст

- Стрічка запису (ADR-0053) приймає вкладення будь-якого типу до 25 МБ. Контракт `lib/timeline` просив лише абсолютну
  адресу `http(s)`, що відкривається без заголовків; кіт відкриває файл посиланням у новій вкладці.
- Логотип і печатка компанії (ADR-0014) приймають SVG. Кіт показує їх через `<img>`, де скрипти не виконуються, але пряме
  відкриття адреси їх виконає.
- API типово на тому самому походженні, що й застосунок, сесія — у cookie. Сервер, що віддає завантажений `.html` чи `.svg`
  зі свого походження з типом за розширенням, дає збережений XSS: скрипт у файлі діє з сесією того, хто файл відкрив.
- Норма цього не називала. Захистити може лише сервер: обмеження типу на клієнті обходиться запитом до API, атрибут
  `download` не діє для іншого походження й не заважає відкрити адресу напряму.

## Рішення

1. **Окреме походження або безпечні заголовки.** Сервер віддає файли користувачів (вкладення стрічки, логотип, печатку,
   підпис, будь-який завантажений файл) з окремого походження без cookie застосунку (наприклад, підписана адреса сховища з
   коротким строком) або з того самого походження лише із заголовками `Content-Disposition: attachment`,
   `X-Content-Type-Options: nosniff` і `Content-Security-Policy: sandbox`.
2. **Тип файла — за вмістом**, а не за розширенням чи типом із запиту. `Content-Type` відповіді — той, що визначив сервер.
3. **SVG** (логотип, печатка, підпис) сервер очищає від скриптів, обробників подій і зовнішніх посилань або не приймає.
4. **Де записано:** шапка контракту `lib/timeline` і `lib/company`, посібник (стрічка запису й налаштування компанії),
   SPEC §17. Клієнт кіта не змінюється.
5. Решту вимог до сервера з безпеки вебу (CSRF, CORS, заголовки відповідей застосунку) цей ADR не вирішує.

## Наслідки

- Бекенд, написаний за контрактом, не відкриває збереженого XSS через файли користувачів.
- Сервер з окремим походженням файлів має давати адресу, що живе довше за відкриту картку (вимога контракту стрічки
  лишається).
- Версії: документація й коментарі контракту, код і типи не змінюються.

## Розглянуті варіанти

- **Лишити на розсуд проекту:** кожен бекенд відкриває цю вимогу сам, а перший пропуск дає XSS від будь-кого з правом
  читання запису.
- **Атрибут `download` на посиланні в стрічці:** не діє для іншого походження й не захищає від прямого відкриття адреси;
  можливий лише як додаток.
- **Заборонити SVG логотипа в контракті:** зміна поля й контракту, а очищення на сервері дає той самий захист без втрати
  векторного логотипа.
- **Обмежити типи файлів на клієнті:** обходиться запитом до API.
