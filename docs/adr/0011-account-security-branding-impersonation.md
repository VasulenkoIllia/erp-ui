# 0011. Налаштування факторів, сесії й пристрої, бренд сторінки входу, «Увійти як…»

- Статус: прийнято (доповнює ADR-0010)
- Дата: 13.10.2026
- Хто ухвалив: власник (вікторина після кроку 0.5b, 13.10.2026)

## Контекст

ADR-0010 закрив вхід: усі способи, відновлення, сесію. Налаштування факторів і список сесій лишалися
на хвилю 1. Власник вирішив зробити їх зараз (крок 0.5b2) і додати ще дві речі:

- брендування сторінки входу з white-label за доменом;
- «Увійти як…» для адміністратора.

Межі ті самі: кіт дає екрани, поведінку, контракт і мок. Справжні TOTP-секрети, WebAuthn-перевірку,
визначення місця за IP і журнал аудиту реалізує бекенд проекту.

## Рішення

1. **Безпека акаунта — `provider.account` (lib/account):**
   - `GET /me/security` — фактори з назвами й датами, що можна додати, залишок резервних кодів,
     вимога компанії, листи про новий вхід;
   - додавання факторів:
     - застосунок: `POST /me/factors/totp` → `{ setupId, secret, uri }` (QR) і `/verify`;
     - SMS/Viber: `POST /me/factors/sms` { phone } і `/verify`;
     - email: `POST /me/factors/email`;
     - ключ доступу: `POST /me/factors/passkey/options` (JSON-форма WebAuthn) і `POST /me/factors/passkey`;
   - `PATCH`/`DELETE /me/factors/:id` — назва й вимкнення;
   - останній фактор, коли компанія вимагає другий крок, — 409 `factor_required`;
   - `POST /me/backup-codes` — нові коди, старі перестають діяти;
   - перший фактор приносить резервні коди, які показуються один раз: копіювати, завантажити, «Я зберіг коди»;
   - зміни факторів — лише після повторного підтвердження (ADR-0010, `useReauth`).
2. **Сесії й пристрої:**
   - `GET /me/sessions`, `DELETE /me/sessions/:id`, `DELETE /me/sessions` — вийти на пристрої або на всіх інших;
   - `GET /me/trusted-devices` і «Забути» (один або всі);
   - `GET /me/sign-ins` — журнал зі сторінками: вхід, невдала спроба, блокування; спосіб, пристрій,
     місце, IP, «Новий пристрій», «Увійти як…»;
   - `PATCH /me/security` { newSignInAlerts } — лист про вхід з нового пристрою;
   - місця й назви — мовою з `Accept-Language`: клієнт API надсилає мову інтерфейсу (`getLanguage`).
3. **Бренд сторінки входу (white-label):**
   - `GET /auth/methods` → `branding`: назва, логотип (світлий і темний), палітра, бічна панель
     (заголовок і текст однією мовою або за мовами, зображення), підтримка, умови, конфіденційність;
   - сервер обирає бренд за доменом;
   - `AuthLayout` показує бренд сам, назва бренду — у заголовку вкладки;
   - палітра бренду — типова для гостя й для користувача без власного вибору
     (`setBrandAppearance`, `useBrandAppearance`);
   - сховище вигляду тепер зберігає лише те, що користувач обрав сам: зміна мови на сторінці входу
     не «заморожує» палітру бренду.
4. **«Увійти як…»:**
   - `POST /auth/impersonation` { userId, reason } → 204: право `users:impersonate`, повторне
     підтвердження, обов'язкова причина;
   - іншого адміністратора — ні (403), себе — ні (422);
   - поки триває: `me.impersonator`, смуга `ImpersonationBanner` у слоті `banner` оболонки, сесія й
     журнал входів користувача показують адміністратора;
   - зміни пароля, email, факторів, сесій і експорт даних — 403 `impersonation_forbidden`;
   - `DELETE /auth/impersonation` — повернення до свого акаунта;
   - сесія лишається однією: вихід завершує її повністю.
5. **QR-код — lean-qr (MIT):**
   - реліз 09.2026, без залежностей, ~4 КБ gzip, SVG через `toSvgPath`;
   - qrcode.react зі SPEC §4 не проходить бар'єр 2 (останній реліз 12.2024);
   - код завжди темний на світлому: нові токени `--scan` / `--scan-foreground` (однакові в усіх
     палітрах і темах), бо інвертовані коди читає не кожен застосунок.
6. **Нові спільні компоненти:**
   - `erp/copy-button` (UI43);
   - `erp/qr-code` (UI32);
   - `SectionSkeleton` у `erp/page-state` — завантаження блоку всередині сторінки.

## Наслідки

- **Пакунок `auth` додатково ставить:** `erp/account-factors`, `erp/account-devices`, `erp/impersonation`.
  `lib/mock-account` — частина `createPlatformHandlers`: опції `branding`, `accountSeeds`,
  `availableFactors`, `twoFactorRequired`.
- **Бекенд проекту має:**
  - зберігати TOTP-секрет лише після підтвердження коду;
  - перевіряти WebAuthn-реєстрацію;
  - писати «Увійти як…» в аудит (A5) з причиною;
  - відповідати мовою з `Accept-Language`.
- **`ADR-0010`:** пункт «налаштування факторів і сесії — хвиля 1» закрито цим кроком.
- **Модуль A2** (користувачі й ролі) у хвилі 1 бере `useImpersonation` для свого списку; демо має лише
  простий список.

## Розглянуті варіанти

- **Окремий `GET /auth/branding`:** ще один запит на першому екрані; бренд у `/auth/methods` приходить
  разом із рештою налаштувань входу.
- **Палітра бренду поверх вибору користувача:** користувач, що обрав «Графіт», втратив би свій вибір;
  бренд — лише типове значення.
- **«Увійти як…» в окремій вкладці з другою сесією:** складніше для бекенду й плутає, хто де.
  Одна сесія зі смугою зрозуміліша, і її легко завершити.
- **qrcode.react / react-qr-code:** бар'єр 2 і зайва React-обгортка; lean-qr менший і без залежностей.
