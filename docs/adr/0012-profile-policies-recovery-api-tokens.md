# 0012. Профіль, політики безпеки організації, втрачений другий крок, токени API

- Статус: прийнято (доповнює ADR-0010 і ADR-0011)
- Дата: 13.10.2026
- Хто ухвалив: власник (вікторина після кроку 0.5b2, 13.10.2026)

## Контекст

Після кроку 0.5b2 у кіті був вхід і безпека акаунта, але бракувало чотирьох речей, без яких
студійний проект не обходиться. Власник обрав зробити їх одразу, кроком 0.5b3:

- профіль користувача;
- політики безпеки компанії;
- допомога тому, хто втратив доступ до другого кроку;
- токени API для інтеграцій.

Межі ті самі, що в ADR-0010/0011: кіт дає екрани, поведінку, контракт і мок. Зберігання, хешування
токенів, справжню перевірку адрес і аудит реалізує бекенд проекту.

## Рішення

1. **Профіль (PF01) — `provider.account`:**
   - `PATCH /me` { name, position, phone, timezone, signature } → 204:
     - відсутнє поле — без змін, `""` — очистити;
     - помилки — 422 `fieldErrors` (`required`, `tooLong`, `invalid`);
   - `/me` повертає `position`, `timezone`, `signature`;
   - контактний телефон — окремо від телефону для кодів у SMS (той — фактор, ADR-0011);
   - фото:
     - `PUT /me/avatar` (multipart, поле `file`) → { avatarUrl };
     - `DELETE /me/avatar`;
   - фото обрізається й стискається в браузері (`erp/avatar-editor`):
     - коло, перетягування, масштаб повзунком і клавішами;
     - результат — квадрат 256 px у WebP, а де браузер не вміє — у PNG;
     - вибраний файл — до 5 МБ, лише JPG, PNG, WebP; сервер однаково перевіряє тип і розмір;
   - часовий пояс — IANA (`Europe/Kyiv`):
     - список із браузера (`Intl.supportedValuesOf`) зі зсувом на сьогодні;
     - застарілі назви (`Europe/Kiev`) показуються сучасними;
     - пошук — новий примітив `ui/combobox` (порт shadcn base-nova).
2. **Токени API (PF17):**
   - `GET /me/api-tokens` → { tokens, scopes }:
     - права для вибору сервер бере з прав користувача і групує за ресурсами;
     - токен не може більше, ніж його власник;
   - `POST /me/api-tokens` { name, scopes, expiresInDays: 30 | 90 | 365 | null } → { token, item }:
     - лише після повторного підтвердження;
     - повний токен показується один раз, у списку — назва, початок токена, дати;
   - `DELETE /me/api-tokens/:id`:
     - відкликання звужує доступ, тому повторного підтвердження не треба;
     - під час «Увійти як…» — 403, як інші зміни безпеки (ADR-0011).
3. **Політика безпеки організації — `provider.admin` (`lib/security-policy`):**
   - `GET /security-policy` → { policy, options }:
     - право `security:read`;
     - `options` — ролі, SSO-провайдери й адреса адміністратора, як її бачить сервер (`currentIp`);
   - `PUT /security-policy` → policy:
     - право `security:update` і повторне підтвердження;
     - помилки — 422 `fieldErrors`: `twoFactorRoles: "required"`, `ipAllowlist.N: "invalid"`,
       `ipAllowlist: "excludesCurrent"` (список відрізав би самого адміністратора);
   - що налаштовується:
     - обов'язковий другий крок: нікому, вибраним ролям, усім;
     - дозволені способи другого кроку;
     - вхід без пароля й SSO-провайдери;
     - пароль: мінімальна довжина (8–64), термін дії, скільки останніх не повторювати;
     - сесія без активності, автовихід після бездіяльності, скільки днів пристрій довірений;
     - дозволені адреси (IPv4/IPv6, CIDR);
   - політика діє на вхід:
     - `GET /auth/methods` віддає вже відфільтровані способи, `passwordPolicy.minLength`, автовихід
       і дні довіри;
     - індикатор складності пароля бере мінімальну довжину звідти.
4. **Обов'язковий другий крок під час входу:**
   - пароль правильний, а фактора ще немає → `{ status: "factor_setup_required", factors }`;
   - на цьому кроці налаштування йде через ті самі `/me/factors/*`, без повторного підтвердження:
     пароль щойно введено;
   - `POST /auth/factor-setup/complete` → результат входу (або 409 `factor_required`, якщо нічого
     не налаштовано);
   - `FactorSetupStep` — у всіх екранах входу:
     - вибір способу, діалоги налаштування, резервні коди;
     - діалоги винесено з `erp/account-factors` у `erp/factor-setup`;
     - поле телефону підставляється ззовні (`PhoneField`), тож libphonenumber не потрапляє на
       сторінку входу (бюджет ADR-0009).
5. **Пароль за політикою:**
   - `password_change_required` має `reason`:
     - `temporary` — тимчасовий;
     - `expired` — минув термін;
     - `policy` — не відповідає вимогам;
   - екран нового пароля пояснює причину;
   - повтор одного з останніх паролів — `fieldErrors: { … "reused" }`.
6. **Дозволені адреси:**
   - вхід з адреси поза списком — 403 `ip_not_allowed` одразу після пароля (або посилання/коду);
   - у журналі входів — «заблоковано»;
   - кіт перевіряє формат (`isValidCidr`) і попереджає адміністратора, справжня перевірка — на сервері.
7. **Втрачений другий крок:**
   - на кроці коду — «Немає доступу до жодного способу?»:
     - `POST /auth/recovery-request` { comment } → 202, лише після правильного пароля;
     - лист користувачу;
   - адміністратор (`users:update`):
     - `GET /recovery-requests`, `DELETE /recovery-requests/:id` — список і відхилення;
     - `POST /users/:id/reset-factors` { reason } → 204 — лише після повторного підтвердження, не
       собі, не під час «Увійти як…»;
     - причина обов'язкова й іде в аудит;
   - скидання прибирає фактори, резервні коди, довірені пристрої й сесії; лист користувачу;
   - далі людина входить паролем, а якщо політика вимагає — одразу налаштовує новий спосіб.
8. **Клієнт API:**
   - `FormData` надсилається як multipart, без заголовка JSON;
   - нові коди помилок: `factor_setup_required`, `ip_not_allowed`.
9. **Нові спільні елементи:**
   - `ui/combobox`, `ui/slider` (порти shadcn base-nova);
   - `erp/timezone-select`, `erp/avatar-editor`, `erp/profile-form`, `erp/api-tokens`;
   - `erp/security-policy-form`, `erp/reset-factors`, `erp/factor-setup`;
   - `lib/security-policy`, `lib/mock-admin`.

## Наслідки

- **Пакунок `auth` додатково ставить** усі нові `erp/*`.
- **Мок:**
  - `createPlatformHandlers` має опції `securityPolicy` (типова політика), `roles` (назви ролей
    мовами), `apiResources` (ресурси для прав токенів);
  - адміністративні обробники входять туди ж.
- **Зміна імпорту:** `BackupCodesDialog` тепер у `erp/factor-setup` (було `erp/account-factors`).
- **Бекенд проекту має:**
  - зберігати лише хеш токена й показувати повний токен один раз;
  - застосовувати політику на сервері: обов'язковий другий крок, пароль, адреси, сесію;
  - брати адресу клієнта з довірених заголовків проксі;
  - обмежувати частоту запитів на відновлення;
  - писати скидання другого кроку в аудит (A5) з причиною й іменем адміністратора;
  - перевіряти тип і розмір фото та зберігати його в сховищі файлів.
- **Модуль A2** (користувачі й ролі, хвиля 1) бере `useResetFactors` і `RecoveryRequestsSection`;
  у демо — простий список.
- **Форматери:** часовий пояс профілю поки лише зберігається. Показ дат у ньому — крок 0.5d.

## Розглянуті варіанти

- **Самостійне відновлення другого кроку листом:**
  - відхилено: хто захопив пошту, отримав би й акаунт;
  - допомога адміністратора з перевіркою особи безпечніша.
- **Тимчасовий обхід другого кроку замість скидання:**
  - відхилено: складніше пояснити користувачу й простіше забути вимкнути.
- **Бібліотека обрізання (react-easy-crop та ін.):**
  - не потрібна: вистачає canvas і Pointer Events;
  - менше залежностей (бар'єри SPEC §18.2).
- **Вшитий список часових поясів:**
  - відхилено: браузер має актуальний список IANA.
