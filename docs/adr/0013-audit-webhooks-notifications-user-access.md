# 0013. Журнал аудиту, вебхуки, налаштування сповіщень, доступ користувачів

- Статус: прийнято (доповнює ADR-0011 і ADR-0012)
- Дата: 13.10.2026
- Хто ухвалив: власник (вікторина після кроку 0.5b3, 13.10.2026)

## Контекст

Після кроку 0.5b3 адміністратор уже керує політиками й допомагає з утраченим другим кроком. Чотири
речі лишалися: кіт генерував події, але не мав де їх показати; токени API давали вхідні інтеграції,
але не вихідні; не було налаштувань сповіщень; не можна було заблокувати акаунт чи побачити сесії
всіх. Власник обрав зробити все кроком 0.5b4.

Межі ті самі: кіт дає екрани, поведінку, контракт і мок. Зберігання журналу, доставку вебхуків з
повторами й надсилання сповіщень реалізує бекенд проекту.

## Рішення

1. **Журнал аудиту — `provider.audit` (`lib/audit`), основа модуля A5:**
   - `GET /audit-events` → { data, total }, новіші першими; право `audit:read`;
   - плоскі фільтри (ADR-0002): `q`, `category` (кілька), `action`, `actorId`, `targetType`, `targetId`,
     `at_gte` / `at_lte`;
   - `GET /audit-events/export` → CSV (UTF-8 з BOM, для Excel) з тими самими фільтрами;
   - подія:
     - `action` — `<розділ>.<дія>`, `category`;
     - `actor` — користувач, токен API чи система; `impersonatedBy`;
     - `target`, `reason`, `changes` («було → стало»), `ip`, `device`, `location`, `details`;
   - назви:
     - дії кіту перекладає кіт;
     - дії проекту — `actionLabels` компонента або `actionLabel` від сервера мовою
       `Accept-Language`;
     - для записів — дієслово: «Зміна запису»;
   - `AuditLog`:
     - пошук, розділ, період, подробиці, експорт;
     - `filter` — історія одного запису (`targetType` + `targetId`) для стрічки запису й модуля A5.
2. **Вебхуки — `provider.webhooks` (`lib/webhooks`), PF11/PF17:**
   - підписка: адреса (лише `https://`, для розробки — `http://localhost`), опис, події, увімкнено;
   - секрет підпису показується один раз; створення, зміна адреси й новий секрет — після повторного
     підтвердження;
   - `POST /webhooks/:id/test` — подія `ping`;
   - журнал доставок: статус, код, тривалість, спроба, запит і відповідь;
   - «Повторити» — та сама доставка (`X-Erp-Delivery`) з наступною спробою;
   - запит до одержувача:
     - тіло `{ id, type, createdAt, data }`;
     - підпис `X-Erp-Signature: t=<unix>,v1=<HMAC-SHA256 секретом від "t.тіло">`;
     - успіх — 2xx за 10 с;
     - повтори: 1 хв, 5 хв, 30 хв, 2 год, 6 год; після 3 діб невдач підписка вимикається.
3. **Налаштування сповіщень — `provider.account` (`lib/notification-settings`), PF10:**
   - `GET` / `PUT /me/notification-settings`: канали проекту, події з розділом, доступними,
     обов'язковими й типовими каналами, вибір користувача, тихі години;
   - обов'язкові (безпека) не вимкнути: сервер відповідає 422;
   - тихі години приглушують push і месенджери, але не застосунок, email і безпеку;
   - `NotificationSettingsForm`:
     - на широкому контейнері — матриця, на вузькому — картки;
     - «Повернути типові»;
     - якщо обрано push, пропонує дозволити сповіщення в браузері (підписка web push — крок 0.5c).
4. **Доступ користувачів — `provider.admin` (`lib/security-policy`), PF01/A2:**
   - `GET /users/:id/access`: стан, хто й чому заблокував, фактори, останній вхід, сесії;
   - `GET /sessions?q=`: активні сесії всіх; `DELETE /sessions/:id` — завершити (свою поточну —
     ні, 409); `POST /users/:id/sign-out` — завершити всі;
   - блокування:
     - `POST /users/:id/block` { reason } — після повторного підтвердження, не себе;
     - сесії завершуються, токени API не діють;
     - `POST /users/:id/unblock`;
   - вхід заблокованого — 403 `account_blocked`, у журналі входів — «заблоковано»;
   - `useUserAccessSheet`, `UserBlockedBadge`, `ActiveSessionsSection`.
5. **Живі дані:**
   - журнал, доставки, сесії й доступ запитуються наново щоразу, коли розділ з'являється
     (`refetchOnMount: "always"`);
   - так вони свіжі, навіть якщо проект кешує запити довше.
6. **Моки:**
   - `lib/mock-audit` сам записує:
     - входи;
     - зміни пароля й факторів;
     - «Увійти як…»;
     - політику з «було → стало»;
     - скидання другого кроку;
     - доступ і токени;
     - вебхуки;
   - `createResourceHandlers`:
     - кожну зміну запису пише в журнал із «було → стало»;
     - надсилає її на шину подій мок-сервера (`emitMockEvent`);
     - нові опції `label`, `titleField`, `fieldLabels`;
   - `lib/mock-webhooks` доставляє події з шини підпискам; результат залежить від адреси:
     `*.invalid` — помилка DNS, `/fail` — 500;
   - `lib/mock-notifications`;
   - `createPlatformHandlers` приймає `auditSeeds`, `webhookEvents`, `webhookSeeds`,
     `notificationChannels`, `notificationEvents`.
7. **Клієнт API:**
   - `responseType: "blob"` — файли (експорт);
   - код `account_blocked`.

## Наслідки

- **Пакунок `auth`** ставить `erp/audit-log`, `erp/webhooks-section`, `erp/notification-settings-form`,
  `erp/user-access`.
- **Права:** `audit:read`, `webhooks:read` / `webhooks:update`; доступ користувачів — `users:update`.
- **Бекенд проекту має:**
  - писати журнал сам (клієнт лише читає), зберігати його незмінним і не коротше, ніж вимагає
    закон;
  - доставляти вебхуки з черги, з підписом і повторами; секрет зберігати зашифрованим;
  - не пускати заблокованого ні паролем, ні кодом, ні SSO, ні токеном API;
  - поважати тихі години й обов'язкові канали під час надсилання сповіщень.
- **Шина подій мок-сервера** — основа реального часу (SSE) у кроці 0.5c.
- **Модулі:**
  - A5 (аудит та історія) будує на `AuditLog` і контракті журналу;
  - A2 (користувачі) — на панелі доступу; у записах користувачів — `status`;
  - PF10 — дзвіник і інбокс поверх налаштувань сповіщень.

## Розглянуті варіанти

- **Журнал на клієнті (ra-core-ee audit log):** платний і не бачить дій сервера (входи, вебхуки) —
  відхилено (SPEC §3, рядок 5).
- **Скачування CSV за посиланням:** простіше, але не працює з моками в браузері й з токеном у
  заголовку; клієнт отримує файл запитом і зберігає його сам.
- **Окремі сторінки для сесій і блокування:** відхилено; усе про доступ людини — в одній панелі з
  рядка списку, а всі сесії компанії — розділом на сторінці користувачів.
