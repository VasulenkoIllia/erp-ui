# 0014. Ролі й матриця прав, запрошення, центр сповіщень, налаштування компанії

- Статус: прийнято (доповнює ADR-0003, ADR-0010 і ADR-0013)
- Дата: 13.10.2026
- Хто ухвалив: власник (вікторина після кроку 0.5b4, 13.10.2026)

## Контекст

Після кроку 0.5b4 адміністратор бачить журнал і керує доступом людей, але чотирьох речей бракувало,
щоб на кіті можна було запустити будь-який проект студії:

- ролі були лише назвами в моку: права не можна було ні подивитися, ні змінити;
- колегу можна було запросити тільки в коді моку — екран прийняття був, а запросити було нікуди;
- дзвіник у топбарі був заглушкою з числом 3;
- реквізитів компанії для рахунків і документів (ЄДРПОУ, IBAN, печатка) не було взагалі.

Власник обрав зробити все кроком 0.5b5. Межі ті самі: кіт дає екрани, поведінку, контракт і мок.
Зберігання ролей, перевірку прав на кожному запиті, надсилання листів і сповіщень реалізує бекенд
проекту.

## Рішення

1. **Ролі й права — `provider.roles` (`lib/roles`), основа модуля A2:**
   - `GET /roles` → { roles, resources }; право `roles:read`;
   - роль: id, назва, опис, `system`, права, `usersCount`:
     - права — рядки `<ресурс>:<дія>`, `<ресурс>:*` або `*` (ADR-0003);
     - `system` — вбудована (власник, адміністратор): лише перегляд, її можна скопіювати;
   - `resources` — каталог прав від сервера мовою `Accept-Language`:
     - ресурс із назвою й розділом;
     - дії ресурсу: `read`, `create`, `update`, `delete`, `export`, `approve`, `impersonate`…;
     - каталог дає проект, тож нові модулі додають свої ресурси без змін кіта;
   - `POST /roles`, `PATCH /roles/:id`, `DELETE /roles/:id`; право `roles:update`:
     - 422: `name` — `required` / `taken`, `permissions` — `invalid` (немає в каталозі);
     - вбудована роль — 403; роль, призначена людям, не видаляється — 409;
   - `PUT /users/:id/roles` { roles }:
     - право `users:update` і повторне підтвердження;
     - хоча б одна роль; свої ролі змінити не можна (щоб не втратити доступ);
   - права людини — об'єднання прав її ролей; `GET /me` віддає їх уже обчисленими;
   - `grants`, `togglePermission`, `countGranted` — для матриці:
     - усі дії ресурсу разом стискаються до `<ресурс>:*`;
     - зняття однієї дії з `*` розгортає решту явно;
   - `RolesEditor`:
     - список ролей із кількістю людей;
     - матриця за розділами: «Усе» для ресурсу (частково — «−») і окремі дії;
     - нова роль, копія, видалення;
     - перехід до іншої ролі з незбереженими змінами питає підтвердження;
   - `RolePicker` і `useRoles` — вибір ролей у запрошенні й панелі доступу;
   - `PermissionGate` — показати вміст лише з правом.
2. **Запрошення — `provider.invitations` (`lib/invitations`), PF01/A2:**
   - `GET /invitations` — ті, що чекають, і прострочені; право `users:create`;
   - `POST /invitations` { email, name?, roles, message? }:
     - лист із посиланням `…/login/invite?token=…`, діє 7 днів;
     - 422: `email` — `required` / `invalid` / `taken` (уже в компанії) / `invited` (уже
       запрошено); `roles` — `required`;
   - `POST /invitations/:id/resend` — новий термін; частіше ніж раз на хвилину — 429;
   - `DELETE /invitations/:id` — посилання більше не діє (410 на екрані прийняття);
   - прийняття — наявний `AcceptInviteScreen` (ADR-0010); людина отримує ролі й компанію з
     запрошення, а той, хто запрошував, — сповіщення;
   - `InvitationsSection` — список, «Запросити колегу», «Надіслати ще раз», «Відкликати».
3. **Центр сповіщень — `provider.inbox` (`lib/notifications`), PF10/UI02:**
   - `GET /notifications?status=all|unread&page=&perPage=` → { data, total, unread };
   - `GET /notifications/unread-count` → { count } — для дзвіника;
   - `PATCH /notifications/:id` { read }; `POST /notifications/read-all`;
   - сповіщення: тип (подія з налаштувань ADR-0013), заголовок і текст мовою `Accept-Language`,
     важливість (`info` / `success` / `warning` / `error`), хто спричинив, `link` у застосунку;
   - сервер надсилає в застосунок лише те, що людина не вимкнула в налаштуваннях;
   - `InboxBell`:
     - лічильник опитується раз на хвилину й при поверненні у вкладку;
     - подія реального часу замінить опитування в кроці 0.5c;
     - панель — 5 останніх, «Прочитати все», «Усі сповіщення»;
   - `NotificationInbox` — «Усі / Непрочитані», позначки прочитаного, «Прочитати все», «Показати
     ще»;
   - перехід за `link` робить роутер проекту (`onNavigate`); відкрите сповіщення стає прочитаним.
4. **Налаштування компанії — `provider.company` (`lib/company`), основа модуля A1:**
   - `GET /company` — поточна компанія (`X-Company-Id`, ADR-0002); читає кожен у компанії;
   - `PATCH /company` — право `company:update`; 422 з кодами LC12;
   - профіль:
     - коротка й повна назва;
     - форма: юрособа (ЄДРПОУ) чи ФОП (РНОКПП);
     - платник ПДВ — ІПН;
     - IBAN і банк (МФО видно з IBAN);
     - адреса, телефон, email, сайт;
     - керівник і посада, головний бухгалтер;
     - палітра компанії (SPEC §6.2) — типова для всіх, хто не обрав свою; `null` — як у бренду;
   - `PUT` / `DELETE /company/logo|stamp` — PNG, JPG, WebP чи SVG до 1 МБ, без обрізання;
   - філії: `POST /company/branches`, `PATCH` і `DELETE /company/branches/:id`;
   - `CompanyProfileForm`:
     - перевіряє як сервер — при виході з поля, далі під час виправлення (SPEC §8.3);
     - без права `company:update` — лише перегляд із поясненням;
   - `CompanyImages`, `CompanyBranchesSection`;
   - `useCompanyProfile` (`hooks/use-company-profile`) — спільний кеш; у корені застосунку
     `useBrandAppearance(useCompanyProfile(Boolean(me)).data?.palette)`: палітра компанії
     важливіша за бренд сторінки входу, вибір користувача — за обидві.
5. **Мок-сервер:**
   - `lib/mock-team`:
     - ролі й призначення в localStorage;
     - права користувачів перераховуються з ролей, якщо всі його ролі описано правами; інакше
       лишаються права з `MockUser` — старі моки працюють без змін;
     - запрошення з листом-посиланням; прийняття — через мок входу;
     - події шини `users.roles_changed` і `users.joined` — щоб проект оновив свій список людей;
   - `lib/mock-inbox`:
     - сповіщення кожного користувача;
     - `pushMockNotification` поважає налаштування «У застосунку»;
     - сповіщення вже надсилають запит на відновлення доступу (адміністраторам, окрім самого
       автора) і прийняте запрошення;
   - `lib/mock-company` — профіль кожної компанії, перевірка реквізитів контрольними сумами LC12;
   - `createPlatformHandlers` приймає `roles` (з правами), `permissionResources`, `inboxSeeds`,
     `companyProfiles`.
6. **Аудит:** зміни ролей, призначення ролей, запрошення (надіслано, прийнято, відкликано) і
   реквізитів пишуться в журнал із «було → стало»; новий розділ журналу — «Компанія».
7. **Примітив `Checkbox`** отримав стан «частково» (`indeterminate`) для «Усе» в матриці.
8. **Фонові запити не продовжують сесію** (доповнює ADR-0010):
   - опитування лічильника йде із заголовком `X-Background-Request: 1` (`background: true` у
     клієнті API);
   - сервер відповідає як завжди, але не зсуває ковзну сесію — інакше відкрита вкладка жила б
     вічно, а попередження «Сесія скоро закінчиться» зникало б само;
   - якщо API на іншому домені, заголовок має бути в `Access-Control-Allow-Headers`.

## Наслідки

- **Пакунок `auth`** ставить `erp/roles-editor`, `erp/permission-gate`, `erp/invitations-section`,
  `erp/notification-inbox`, `erp/company-settings`.
- **Права:** `roles:read` / `roles:update`, `users:create` (запрошення), `company:update`.
- **Бекенд проекту має:**
  - перевіряти права на кожному запиті з ролей (клієнт лише ховає недоступне);
  - не дозволяти змінювати вбудовані ролі й свої ролі;
  - надсилати листи запрошень і зберігати токен запрошення лише як хеш;
  - поважати налаштування сповіщень під час надсилання;
  - не продовжувати сесію запитами з `X-Background-Request: 1`;
  - зберігати реквізити й перевіряти їх так само, як клієнт.
- **Модулі:**
  - A1 бере `CompanyProfileForm` і контракт компанії; мультивалюта й локалізація — там же;
  - A2 — `RolesEditor`, `InvitationsSection`, панель доступу;
  - K2 (рахунки) бере реквізити, логотип і печатку для друку (крок 0.5c).
- **Дзвіник** — `InboxBell`; `NotificationBell` лишився примітивом без даних.

## Розглянуті варіанти

- **Ролі лише в коді проекту, без редактора:** простіше, але кожен клієнт студії просить «ще одну
  роль»; редактор із каталогом прав від сервера закриває це раз і назавжди.
- **Права на рівні полів і записів (ABAC):** потрібні не всім проектам і сильно ускладнюють UI;
  відкладено до модуля A2 (хвиля 1), контракт `<ресурс>:<дія>` цьому не заважає.
- **Сповіщення через сторонній сервіс (Novu, Knock):** ще одна залежність у кожному проекті й дані
  користувачів у третьої сторони; контракт простий — бекенд реалізує його сам або ставить такий
  сервіс у себе за цим контрактом.
- **Обрізання логотипа й печатки:** редактор фото профілю (ADR-0012) квадратний; печатка має бути
  як є, з прозорим тлом — тому без обрізання.
