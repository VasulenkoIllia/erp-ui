# 0002. Формат API

- Статус: прийнято
- Дата: 13.10.2026
- Хто ухвалив: власник (вікторина 13.10.2026)

## Контекст

Кіт лише фронтендовий (SPEC §1): бекенд кожного проекту пишеться під контракти кіта.
Тому формат API має бути один для всіх модулів:

- його розуміє dataProvider ra-core (SPEC §4);
- його відтворюють моки MSW (SPEC §17);
- його легко реалізувати на будь-якому бекенді — Laravel, NestJS, Go.

SPEC §17 уже задав формат помилок, гроші в мінорних одиницях і версію запису для конфліктів.
Лишалися відкритими:

- синтаксис фільтрів, сортування й пагінації;
- як передається компанія (PF02);
- як клієнт поводиться з конфліктом.

## Рішення

1. **Ресурсні REST-ендпоінти** з префіксом `/api/v1`:
   - `GET /<ресурс>` — список;
   - `GET /<ресурс>/<id>` — запис;
   - `POST /<ресурс>` — створення (201 і запис);
   - `PATCH /<ресурс>/<id>` — зміна лише переданих полів;
   - `DELETE /<ресурс>/<id>` — 204.
   Ресурс ra-core = сегмент шляху (`invoices` → `/api/v1/invoices`).
2. **Список — плоскі параметри запиту** (вибір власника):
   `status=paid&status=sent&amount_gte=10000&q=агро&sort=-date,number&page=2&perPage=50`.
   - Повтор ключа — «одне з» (`status=paid&status=sent`).
   - Суфікси операторів: `_gte`, `_lte`, `_gt`, `_lt`, `_ne`; без суфікса — рівність.
   - `q` — повнотекстовий пошук по полях, які обирає сервер.
   - `sort` — поля через кому, `-` — за спаданням.
   - `page` з 1; `perPage` до 500, за замовчуванням 25.
   - Відповідь — `{ data: T[], total: number }`.
   - `getMany` у ra-core — той самий список із фільтром `id=1&id=2`.
3. **Помилки** — єдиний формат SPEC §17 і HTTP-статус:
   `{ code, message, fieldErrors?, providerCode?, providerMessage?, current? }`.
   - Коди: `validation` (422), `unauthenticated` (401), `forbidden` (403), `not_found` (404),
     `conflict` (409), `rate_limited` (429), `server` (5xx).
   - Мережевий збій клієнт перетворює на `offline` зі статусом 0.
   - Користувач бачить текст за кодом мовою інтерфейсу (`hooks/use-api-error-message`).
     `message` сервера — для журналу.
4. **Конкурентне редагування** — поле `version` (ціле, з 1) у кожному записі:
   - PATCH надсилає `version`, з якою відкрилась форма;
   - розбіжність → 409 `conflict` з актуальним записом у `current`;
   - клієнт показує `erp/conflict-dialog`:
     - «Зберегти мої зміни» — повтор із `version: current.version`;
     - «Взяти збережене» — форма отримує збережену версію.
5. **Компанія — заголовок `X-Company-Id`** (вибір власника):
   - сервер обмежує дані цією компанією й перевіряє, що вона доступна користувачу;
   - без заголовка — компанія за замовчуванням із профілю.
6. **Сесія — httpOnly cookie** (ADR-0003). Клієнт завжди шле `credentials: "include"`, токенів у JS немає.
7. **Реалізація в кіті:**
   - `lib/api` — конвенції, `ApiError`, HTTP-клієнт `createApiClient` (необов'язкова zod-схема відповіді);
   - `lib/data-provider` — dataProvider ra-core:
     - update надсилає лише змінені поля + `version`;
     - `updateMany`/`deleteMany` поки виконують запит на кожен запис;
   - `lib/mocks` — MSW-обробники за тим самим контрактом (фільтри, сортування, пагінація, права, версії, компанії);
   - `lib/mock-scenarios` і `erp/dev-panel` — сценарії `success`, `error`, `empty`, `slow`, `conflict`, `forbidden`, `offline`.

## Наслідки

- Модулі хвиль 1–5 описують лише схеми ресурсів (`contract.ts`); транспорт, помилки й моки беруться з кіта.
- Бекенд реалізує один парсер списку для всіх ресурсів. Розбір параметрів для TypeScript-бекенду —
  `fromSearchParams` з `lib/api`.
- Масові операції з частковою невдачею (SPEC §8.5) — окремий ендпоінт на кроці 0.6: зроблено в
  0.6c2 як фонова задача сервера, `POST /<ресурс>/bulk/<дія>` і `/jobs/:id` (ADR-0018).
- `X-Company-Id` має бути в CORS `Access-Control-Allow-Headers`, якщо API на іншому домені.
- Сценарій `conflict` у моках спрацьовує один раз на запис: так перевіряється і діалог, і перезапис.

## Розглянуті варіанти

- **Фільтр одним JSON-параметром** (`filter={"status":["paid"]}`, як у ra-data-simple-rest):
  - ближче до ra-core;
  - гірше читається в логах і закладках;
  - незручно реалізовувати на бекенді;
  - власник обрав плоскі параметри.
- **`range`/`Content-Range`** (ra-data-simple-rest): заголовки губляться в проксі й CORS; `{ data, total }` у тілі простіше.
- **ETag/If-Match замість `version`**: стандартно для HTTP, але незручно в батчах і моках; `version` у тілі видно в DevTools.
- **Компанія в шляху** (`/companies/<id>/invoices`) — довші URL і подвоєні маршрути; **у сесії** — неможливо працювати з двома компаніями у двох вкладках.
