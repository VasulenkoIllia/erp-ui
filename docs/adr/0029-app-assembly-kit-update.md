# 0029. Збирання застосунку й оновлення кіта однією командою

- Статус: прийнято (доповнює ADR-0004, ADR-0008, ADR-0010 і ADR-0020)
- Дата: 20.10.2026
- Хто ухвалив: власник (вікторина наприкінці 1.8 і вікторина на старті 1.9, `docs/WAVE-1.md`) /
  власник

## Контекст

Тестовий проект `erp-ui-pilot` (кроки 1.5b–1.8) зібрав застосунок із кіта, але ~100 рядків
оболонки написав сам, бо в кіті їх не було: браму сесії (спінер, помилка профілю з повтором, гість →
вхід), маршрути екранів входу, вихід із повідомленням, рівень заголовка `PageState` на сторінці
«Не знайдено», останню крихту посиланням (список над карткою), автовихід за політикою сервера без
ручного `useAuthMethods`, політику повторів `QueryClient` і помічники e2e. Наступний проект
написав би їх утретє.

Оновлення кіта в проекті (кроки 1.7b і fix-use-client) — 6–7 команд руками: архів тегу, `shadcn
build`, `add --dry-run`, `add --overwrite --yes` усіх встановлених елементів, повернути закріплення
CLI (його знімає залежність `shadcn` у `base` і `tokens`), перезаписати відбитки `kit-files.json`.

Власник вирішив (вікторина наприкінці 1.8): крок 1.9 — готові частини, одна команда оновлення,
`base` і `tokens` без залежності `shadcn`, випуск v1.0.0. Вікторина на старті 1.9: команда —
файлом кіта в проекті; застосовує зміни одразу після звіту (без окремого підтвердження, git
показує все); читання повторюються один раз тихо; власний код тестового проекту, який замінили
частини кіта, видаляється.

## Рішення

1. **`erp/app-gate`**:
   - `SessionGate` — частина застосунку лише для тих, хто увійшов (зазвичай `AppShell` з усіма
     сторінками). Гість — на `/login` (ra-core поверне на ту саму адресу), поки сесія й профіль
     перевіряються вперше — спінер; повторна перевірка («Увійти як…» і вхід в іншій вкладці скидають
     дані, зокрема перевірку сесії ra-core) оболонку не прибирає, інакше губилось би незбережене.
     Профіль не завантажився (мережа, 5xx) — `PageState` з h1 і «Спробувати ще» в `<main>`, а не
     вічний спінер і не «Увійти»: людина, можливо, вже увійшла; поки повтор іде, стан лишається на
     місці, щоб фокус не губився. Далі — вміст і `SessionGuard` з параметрами брами
     (`idleMinutes`, `warnSeconds`): окремо його не ставлять.
   - `useSignOut()` — вихід для меню користувача: «Ви вийшли», а якщо сервер не завершив сесію —
     помилка, щоб людина не думала, що вийшла. Повторне натискання під час виходу нічого не робить.
2. **`erp/auth-routes`**: `createAuthRoutes(options)` → `{ routes, preload }` — маршрути React
   Router усіх екранів входу (вхід, «Забули пароль», новий пароль і запрошення з токеном з адреси,
   посилання для входу, реєстрація, повернення з SSO) лінивими чанками, `preload(pathname)` — чанк
   екрана для поточної адреси. Адреси — `AUTH_ROUTE_PATHS` (ті, що вже знають екрани входу); усі,
   крім входу, можна змінити: на `/login` ra-core 5 веде гостя й після виходу, і змінити це не можна
   (`defaultAuthParams.loginUrl`). Кожен екран — у своїй межі помилок з h1: чанк, що не
   завантажився, не лишає людину без входу. Екрани входу — поруч із `SessionGate`, а не всередині.
3. **`erp/page-state`**: `headingLevel` 1 | 2 | 3, за замовчуванням 2 (стан під h1 сторінки); 1 —
   стан замість усієї сторінки («Не знайдено» картки, помилка профілю); 3 — стан секції чи вкладки.
4. **`erp/app-shell`**: остання крихта з `href` — посилання (список над карткою запису), без
   `href` — поточна сторінка, як було; не остання без `href` — підпис групи, без `aria-current`
   (раніше поточних сторінок у крихтах бувало дві).
5. **`erp/session-guard`**: без пропса `idleMinutes` — політика сервера (`idleTimeoutMinutes` з
   `GET /auth/methods`; поки її не завантажено, діє лише термін сесії сервера),
   `idleMinutes={null}` — лише термін сесії сервера. З явним `idleMinutes` політику не запитує
   (`useAuthMethods({ enabled })`). Проект більше не читає `useAuthMethods` сам.
6. **`lib/query-client`**: `createQueryClient()` — читання повторюються один раз через 1 с лише
   після тимчасового збою (офлайн, 5xx); 4xx (401, 403, 404, 409, 422, 429) і помилки коду — без
   повтору, людина бачить стан одразу; браузер уже офлайн — теж без повтору: повтор TanStack Query
   став би на паузу, і людина бачила б спінер замість «Немає з'єднання». Зміни (`mutations`) — без
   повтору (неідемпотентний запис без ключа ідемпотентності не повторюємо) і без паузи без мережі
   (`networkMode: "always"`, як уже у формі запису); `staleTime` 30 с.
7. **Шар `tools`** (новий, «Інструменти проекту»):
   - `tools/kit` — команда кіта в проекті: `scripts/erp-ui-kit.mjs` і `scripts/erp-ui-kit-lib.mjs`
     (з v1.0.1 — ще `scripts/erp-ui-kit-deps.mjs`, доповнення fix-kit-deps). Ті самі файли входять у
     `base`, тож команда є в кожному проекті з кітом.
   - `tools/e2e` → `e2e/erp-ui.ts`: `openAs` (користувач моків і вигляд до завантаження сторінки),
     `expectNoA11yViolations` (axe, WCAG 2.2 AA), `expectNoHorizontalScroll`, `cellOf`, меню й
     підменю. Залежності — `@playwright/test`, `@axe-core/playwright` у `devDependencies`. Ключі
     сховища в помічниках — копії ключів кіта (у Node Playwright код застосунку не імпортується);
     модульний тест кіта не дає їм розійтися.
8. **Команда оновлення** (у корені проекту):

   ```bash
   node scripts/erp-ui-kit.mjs update v1.0.0 --dry-run   # що зміниться
   node scripts/erp-ui-kit.mjs update v1.0.0             # оновити
   node scripts/erp-ui-kit.mjs check                     # файли кіта не правлені (у pnpm lint і CI)
   ```

   - Порядок: чисте git і незмінені файли кіта → тег архівом одним запитом (`gh api
     repos/VasulenkoIllia/erp-ui/tarball/<тег>`, тайм-аут 120 с, повтори через 5 і 30 с після
     збою мережі, 5xx чи 429; на 401, 404, вичерпаному ліміті й інших 4xx — зупинка з поясненням)
     → перевірка, що це `registry.json` кіта (`homepage` — адреса репозиторію) й версія тегу
     збігається з `package.json` → `shadcn build` закріпленою CLI проекту → `add --dry-run` (звіт:
     зміниться, нові, без змін; порожній чи нерозпізнаний звіт — помилка) → `add --overwrite
     --yes` → файли, які проект доповнює сам, лишаються його → закріплення CLI → повторний
     `--dry-run`: усе, крім файлів проекту, — `skip` → нові відбитки (запис через тимчасовий файл).
     З v1.0.1 залежності елементів ставить команда, а не CLI, і «закріплення CLI» вже не потрібне
     (доповнення fix-kit-deps).
   - Збій після `add` — `kit-files.json` лишається старим, команда пише, як побачити й повернути
     зміни (`git diff`, `git restore .`); так само на Ctrl+C. Кожна команда має тайм-аут (10 хв,
     завантаження — 120 с), причину збою shadcn (він пише її в stdout) показано.
   - Межа довіри — доступ на запис до приватного репозиторію кіта: команда бере лише його архів
     (`gh api` з токеном людини) і не виконує з нього нічого, крім `shadcn build` і `add`.
   - `kit-files.json`: `kit` (версія), `items` (встановлені елементи — наступне оновлення бере їх
     звідси; новий — `--add`, перший раз — `--items`), `files` (sha256 файлів кіта), `own`
     (відбитки версій кіта файлів проекту). Формат `files` — той самий, що писав тестовий проект.
   - Файли, які проект доповнює сам (`src/index.css`, `docs/erp-ui/CLAUDE.project.md`), не
     перевіряються: якщо проект їх змінював, команда лишає версію проекту й показує різницю з
     новою версією кіта. Файли, які git ігнорує (напр. `.claude/skills` у
     `.git/info/exclude`), у відбитки не входять: у чистій копії CI їх немає.
   - Файлів, яких у новій версії немає, команда не видаляє, а лише називає.
   - Гілка чи коміт кіта (пробна несумісна зміна, ADR-0020, доповнення 1.7c) — `--from <шлях до
     копії кіта>`: `git archive` лише реєстру й файлів, на які він посилається.
   - Перший раз (у проекті ще немає команди) — завантажити два файли команди з тегу в тимчасову
     теку й запустити звідти (`docs/using-erp-ui.md`, розділ 8).
9. **`base` і `tokens` без залежності `shadcn`**: вона лише оголошувала CLI, а `add` переписував
   закріплену версію проекту на діапазон. CLI проект закріплює сам (`docs/using-erp-ui.md`,
   розділ 1).
10. **Версія 1.0.0** — оголошення стабільного API (CLAUDE.md, правило 8), а не несумісна зміна:
    усе нове — доповнення, файли розширення й адаптери проекту не змінюються.
11. **Демо** бере `useSignOut`, `createQueryClient`, `headingLevel` («Не знайдено» картки модуля —
    h1, сторінка «Стани» — стан секції h3) і помічники e2e з `registry/tools/e2e.ts`. `SessionGate`
    і `createAuthRoutes` демо не бере: його сторінки відкриті й гостю (галерея компонентів), а
    екрани входу — окрема сторінка демо з усіма варіантами входу. Їх перевіряють модульні тести
    кіта й тестовий проект.

## Наслідки

- Проект збирає застосунок із частин кіта: `SessionGate` + `AppShell` + `createAuthRoutes` +
  `useSignOut` + `createQueryClient`; власний код оболонки — лише навігація й крихти проекту.
- Оновлення кіта — одна команда; звіт `--dry-run` читається з формату CLI 4.22, інший формат —
  помилка, а не порожній список (проект оновлює CLI разом із кітом).
- `pnpm lint` проекту — `node scripts/erp-ui-kit.mjs check` замість власного скрипта.
- Каталог має шар «Інструменти проекту» (`tools/kit`, `tools/e2e`).
- `consumer-smoke` встановлює й нові елементи (вони в шарах `erp`, `lib`, `tools`).

## Розглянуті варіанти

- Команду щоразу скачувати з кіта, без файлу в проекті, — відхилено власником: команда не
  закріплена за версією кіта й не видна в історії проекту.
- Питати «Застосувати?» після звіту — відхилено власником: не працює без людини (CI, агент) і
  додає крок; звіт друкується перед записом, а чисте git показує кожну зміну й дає повернути все
  `git restore .`.
- Без автоматичних повторів, помилка одразу (як було) — відхилено власником: короткий збій мережі
  давав хибну помилку; один тихий повтор через 1 с її прибирає, а 4xx і зміни не повторюються.
- `SessionGuard`, який проект ставить окремо від брами, — відхилено: проект ставив би охорону
  сесії двічі чи забував би її; брама ставить її сама й передає їй свої параметри.
- Своя адреса входу (`paths.login`) — відхилено: ra-core 5 веде гостя й після виходу лише на
  `/login`; підтримка іншої адреси потребувала б `redirectTo` з `checkAuth` і `logout`
  провайдера — коли попросить проект.

## Доповнення fix-kit-deps (21.10.2026, v1.0.1)

Контекст. Тестовий проект, оновлюючись на v1.0.0, отримав `"@axe-core/playwright": "^4.14.0"` замість
свого `~4.14.0` (повернуто руками). Відтворено на копії проекту: команда v1.0.0, `update v1.0.0`
тієї самої версії змінює лише цей рядок у `package.json` і `pnpm-lock.yaml`. Причина — у CLI
shadcn 4.22.0 (`updateDependencies`, `@shadcn/registry` 0.2.0): залежність елемента з версією
(`назва@діапазон`, так їх пише `build-registry`) він ставить завжди, навіть наявну в проекті, —
`pnpm add -- назва@діапазон` для всіх залежностей усіх оновлюваних елементів; пропускає лише
наявну без версії. pnpm 12 лишає версію з lock-файла, якщо вона в діапазоні кіта, але пише
діапазон `^<версія>`, а версію поза діапазоном кіта підняв би, зокрема до нової мажорної. Опції
«без залежностей» в `add` немає.

Рішення (вікторина наприкінці 1.9: діапазони й версії проекту лишаються, нові залежності
ставляться):

1. Після `shadcn build` команда забирає `dependencies` і `devDependencies` з файлів елементів
   зібраного реєстру: CLI їх не бачить і менеджер пакетів не запускає.
2. Залежність, якої в `package.json` проекту немає (у `dependencies`, `devDependencies`,
   `optionalDependencies` чи `peerDependencies`), команда ставить сама з діапазоном кіта
   менеджером пакетів проекту — одним викликом для застосунку й одним для розробки (назви — після
   `--`). Пакет, потрібний застосунку хоч одному елементу, — у `dependencies`. Менеджер — з поля
   `packageManager`, інакше за найближчим lock-файлом у проекті чи вище, до кореня git-репозиторію
   включно (корінь воркспейсу; pnpm, yarn, bun з `bun.lockb`, npm з `npm-shrinkwrap.json`;
   чужий lock-файл вище, напр. у домашній теці, — не проекту); lock-файли різних менеджерів в
   одній теці без `packageManager` — помилка. Не вдалося визначити, а ставити треба, — зупинка ще
   до запису файлів: npm, який вгадував би CLI shadcn, переклав би `node_modules` іншого
   менеджера. Менеджер визначається перед записом завжди (і в `--dry-run` — та сама помилка), а
   `<менеджер> --version` запускається, коли є що ставити.
3. Наявні залежності не змінюються ні в `package.json`, ні в lock-файлі. Якщо встановлена версія
   (`node_modules/<назва>` у проекті чи вище) не в діапазоні кіта (`^`, `~` чи точна версія, як
   у semver; пререліз у діапазон без пререлізу не входить), незрозуміла чи не встановлена, звіт
   перед записом її називає (`! назва: кіт чекає …, у проекті …`), а версію лишає проекту:
   оновити — рішення проекту, підказку дає `CHANGELOG.md` кіта. Наприкінці попередження
   повторюються. Діапазони кіта — лише такого вигляду: `build-registry` інший не пропустить, а
   команда не прийме залежності елемента з іншим записом чи різними діапазонами одного пакета.
4. Зупинки з поясненням і підказкою, як повернути зміни (`kit-files.json` не змінюється): звіт
   `add --dry-run` має секцію `Dependencies` чи `Dev Dependencies` (CLI ставив би їх сам) — ще до
   запису; `add` змінив `package.json` чи lock-файл (інша версія CLI); після встановлення
   змінився діапазон, що був, нова залежність не встановилась чи з'явився lock-файл іншого
   менеджера (свій може з'явитись уперше — проект з `packageManager` без lock-файлу) — код
   виходу менеджера не доказ. Попередження наприкінці — з версіями після встановлення: менеджер
   міг доставити й наявні.
5. Повернення закріплення CLI прибрано: залежність `shadcn` CLI більше не ставить, а сам `shadcn`
   у проекті завжди є (без нього команда не запускається).
6. Код залежностей — третій файл команди `scripts/erp-ui-kit-deps.mjs` (у `tools/kit` і `base`):
   інакше `erp-ui-kit-lib.mjs` переріс би 400 рядків.
7. З v1.0.0 на v1.0.1 проект переходить командою v1.0.1 (три файли з тегу в тимчасову теку,
   `docs/using-erp-ui.md`, розділ 8): команда v1.0.0 ще віддає залежності CLI (вікторина на
   старті fix-kit-deps, 21.10.2026).
8. Перший запуск без списку елементів у `kit-files.json` вимагає `--items` і з `--add`: інакше
   список склав би лише новий елемент, і `base` випав би з оновлень і `check`.

Перевірено: модульні тести команди (розбір залежностей, діапазони, план, визначення менеджера —
`packageManager`, lock-файл воркспейсу, `bun.lockb`, кілька lock-файлів, межа — корінь git;
звірка після встановлення з першим lock-файлом свого менеджера) і повний `update` з
підробленими CLI shadcn і менеджерами пакетів (`scripts/erp-ui-kit-update.test.mjs`: наявні
діапазони лишаються, нові — одним викликом для застосунку й одним для розробки, `--dry-run`
нічого не пише, версія поза діапазоном — попередження й наприкінці, зупинки: звіт обіцяє
залежності, зокрема лише для розробки, менеджер не визначити, CLI змінив `package.json`, збій
менеджера, менеджер переписав наявний діапазон; `packageManager` без lock-файлу — ставить ним); на копії тестового проекту зі справжніми CLI 4.22.0 і pnpm 12 —
`update v1.0.0` не змінив ні `package.json`, ні `pnpm-lock.yaml`, а без `lean-qr` у проекті
команда поставила лише `lean-qr@^2.7.4`, і обидва файли стали такими самими, як до видалення.

Прогрів екрана входу (той самий крок): проект з брамою сесії вантажить екран входу, коли браузер
вільний, — `useEffect(() => whenIdle(() => auth.preload()), [auth])` (`lib/lazy`), як тестовий
проект; `auth.preload(pathname)` — для адреси, з якою гість відкрив застосунок. Підказки, які
`add` друкує після пакунка `auth`, — `createAuthRoutes` і `SessionGate`, а не маршрути руками й
`SessionGuard` з `idleMinutes`.

Розглянуті варіанти:

- Дати CLI поставити залежності й повернути діапазони після `add` — відхилено: lock-файл
  лишився б з переписаним `specifier`, а версія, яку CLI підняв у діапазоні кіта, — піднятою.
- Залежності в реєстрі без версії (CLI пропускає наявні) — відхилено: нова залежність ставилась
  би найновішою, а не перевіреною з кітом, і так само — у новому проекті через `shadcn add`.
- Ставити версію кіта, коли версія проекту поза діапазоном кіта, — відхилено: версія залежності —
  рішення проекту (вікторина 1.9); команда лише попереджає.
