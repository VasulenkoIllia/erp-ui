# 0020. Точки розширення модуля: зміни під клієнта поза файлами модуля

- Статус: прийнято (принцип; форма типів спільного шару — крок 1.2, розділ «Форма типів»; фабрика модуля, фільтри, вкладки, статуси й рядки — крок 1.4a, розділ «Форма типів модуля», ADR-0025; поля у формі — крок 1.4b; рядки «Подробиць», журнал і `change` статусів — крок 1.7, розділ «Доповнення: крок 1.7»; як оформлювати несумісну зміну — крок 1.7c, розділ «Доповнення: крок 1.7c»). Доповнює ADR-0004; для модулів змінює SPEC §3.3
- Дата: 15.10.2026
- Хто ухвалив: власник (обговорення й вікторина 15.10.2026)

## Контекст

Модуль ставиться в проект копіюванням коду (SPEC §2 №2, ADR-0004). Оновлення: `shadcn add --diff`
→ `shadcn add`. Локальна правка позначається `// erp-ui: local override — <причина>` і видна в
диффі (SPEC §3.3).

Для окремого компонента цього досить. Модуль — це десятки файлів: контракт, моки, сторінки, рядки.
А кожен клієнт хоче своє: поля, колонки, статуси, вкладки. Приклад — B1 «Контакти й компанії» в
клієнтському проекті:
- картка клієнта зі своїми вкладками;
- поля, яких немає в загальному B1.

Якщо правити файли модуля, кожне оновлення в кожному проекті стає ручним зведенням диффів. З
десятком проектів оновлення просто перестануть ставити. Це перший із трьох ризиків, названих в
обговоренні 15.10.2026 (`docs/WAVE-0.md`, «Після хвилі 0»).

Окремо від цього рішення — PF09 і A3 «Кастомізація без коду» (хвиля 2): там те саме налаштовує
адміністратор у працюючій системі. Тут — розробник проекту в коді.

## Рішення

1. **Файли модуля в проекті не правляться.** Усе, що відрізняє клієнта, лежить в окремому файлі
   розширення проекту: `src/extensions/<ID>-<назва>.ts(x)`, напр. `src/extensions/B1-contacts.tsx`.
   Цей файл не належить жодному елементу реєстру, тому `shadcn add` його не створює й не
   перезаписує.
2. **Що змінюється в розширенні** (точки розширення):
   - **поля:** додати поле (zod-схема, підписи uk/en, поле вводу з кіта), сховати поле модуля,
     порядок і групи у формі й картці; обов'язкові поля контракту не ховаються;
   - **колонки списку:** додати (зокрема з нового поля), сховати, порядок, пріоритет на вузькому
     екрані;
   - **фільтри й вкладки-статуси списку:** додати, сховати;
   - **статуси:** додати чи перейменувати статус, тон — лише зі статусних токенів (§6.3), дозволені
     переходи;
   - **картка:** додати секцію чи вкладку (компонент проекту в слоті шаблону Object Page), сховати
     чи переставити секції модуля;
   - **дії:** додати дію в шапку картки, у рядок чи масову, з правом `<ресурс>:<дія>`; сховати дію
     модуля, зокрема ту, якої не вміє бекенд (ADR-0021);
   - **рядки:** перевизначити тексти модуля (ключі i18n модуля) і додати тексти нових полів;
   - **моки й демо-дані:** значення нових полів у фікстурах, щоб проект працював на моках без
     бекенду.
3. **Як модуль отримує розширення.** Модуль не імпортує файлів проекту. Точка входу модуля
   (`index.ts`, SPEC §17) експортує фабрику `create<Модуль>Module(extension?)` і тип розширення
   `<Модуль>Extension`. Проект викликає фабрику в одному своєму місці (маршрути застосунку) і
   передає розширення. Фабрика повертає ресурси ra-core, маршрути й пункти навігації. Без розширення
   модуль працює так само, як у демо кіта.
4. **Розширення — це дані й компоненти в слотах, а не перевизначення коду модуля.**
   - Схема нового поля розширює схему контракту (`schema.extend`): додаткові поля проходять
     перевірку і у формі, і у відповідях бекенду (SPEC §18.4).
   - Елементи (поля, колонки, фільтри, статуси, секції, дії) мають ключі: розширення додає, ховає
     чи переставляє елемент за ключем, не знаючи, як модуль його будує.
   - Компонент у слоті отримує запис і ресурс (`RecordSlotProps`), права бере з `useCanAccess`, мову —
     з `useLanguage`, тобто з публічного API кіта, а не з внутрішнього стану модуля (уточнено на
     кроці 1.2).
5. **Модуль тонкий, складне — у спільних шарах.**
   - Модуль — це контракт, моки, фікстури, рядки й налаштування шаблонів SPEC §7: сторінки модуля
     збирають List Report, Object Page та інші з `templates`, `erp` і `lib`, а не мають власної
     розкладки.
   - Таблиця, фільтри, форма, картка, стрічка, статуси й самі точки розширення живуть у спільних
     шарах. Їх оновлюють один раз для всіх модулів.
   - Модулю потрібен новий компонент чи нова точка розширення — вони з'являються в спільному шарі
     (CLAUDE.md, правило 1), а не всередині модуля.
6. **Оновлення без ручного зведення.**
   - `npx shadcn add VasulenkoIllia/erp-ui/modules/<ID>-<назва>#vX.Y.Z --diff` показує лише зміни
     кіта: локальних правок у файлах модуля немає (як це працює насправді — реєстр з тегу локально,
     `--dry-run`, `--overwrite` — доповнення 1.7, «Умови оновлення»);
   - `shadcn add …` перезаписує файли модуля, потім `tsc` і тести проекту;
   - несумісна зміна типу розширення — це зміна публічного API модуля: мажорна версія (CLAUDE.md,
     правило 8) і розділ «Як оновити розширення» в `CHANGELOG.md`. TypeScript показує, що змінити, у
     файлі розширення, а не в модулі.

   Умови. Елемент реєстру несе всі свої файли (ADR-0004, п. 3), тож `shadcn add` модуля
   перезаписує й потрібні йому файли спільних шарів (`templates/*`, `erp/*`, `ui/*`, `lib/*`,
   `hooks/*`). Без ручного зведення оновлення ставиться, коли в проекті немає непозначених правок цих
   файлів (позначені `local override` видно в `--diff`, п. 7), а код проекту (розширення, адаптер
   ADR-0021) спирається лише на публічний API кіта.
7. **Чого бракує — у кіт, а не в модуль проекту.**
   - Немає потрібної точки розширення — вона додається в кіт (PR в erp-ui), проект оновлює модуль.
   - Якщо чекати не можна, проект «від'єднує» модуль: копіює його під іншою назвою у свій код і
     більше не оновлює з кіта. Рішення записується в README проекту.
   - Позначка `// erp-ui: local override` лишається лише для елементів спільних шарів (`ui/*`,
     `erp/*`, `templates/*`, `lib/*`, `hooks/*`, SPEC §3.3). Для модулів вона не застосовується.
8. **Перевірка в кіті.**
   - Демо показує кожен модуль і з прикладом розширення: додаткове поле, колонка, статус, секція.
   - Перевірка доставки в CI (`pnpm consumer-smoke`, ADR-0004) ставить модуль із розширенням у
     чистий проект і збирає його.
   - Модуль без точок розширення в реєстр не приймається.
9. **Зв'язок із PF09 і A3.** Кастомізація без коду (хвиля 2) використає ті самі точки розширення:
   власні поля, порядок полів, статуси й колонки від адміністратора — це розширення, що приходить із
   сервера як дані. Тому все, крім компонентів у слотах, описується даними (тип поля, підпис,
   обов'язковість, тон статусу), без функцій.

## Форма типів (крок 1.2)

Спільний шар — `lib/extensions`, `lib/extension-fields`, `templates/object-page`
(`useRecordSlots`):

```ts
// lib/extensions — без React і без інших файлів кіта
interface Keyed { readonly id: string }
type Placement<K extends string = string> =
  "start" | "end" | { readonly before: K } | { readonly after: K }  // одне з двох
type Placed<T, K> = T & { readonly place?: Placement<K> }
interface KeyedChanges<T extends Keyed, K extends string = string> {
  readonly add?: readonly Placed<T, K>[]                        // ключ модуля — заміна елемента
  readonly hide?: readonly K[]                                  // крім закріплених (`locked`)
  readonly move?: readonly { readonly id: K; readonly place: Placement<K> }[]
}
applyKeyedChanges<T, A = T>(items: T[], changes?: KeyedChanges<A, T["id"]>, { locked? }): (T | A)[]
mapKeyedChanges(changes, (item) => element)                    // дані розширення → елементи шаблону

// lib/extension-fields
type ExtensionField = { id: string; label: LocalizedText; required?: boolean; mockValues?: ExtensionFieldValue[] }
  & ({ type: "text" | "number" | "date" | "boolean" } | { type: "options"; options: { value: string; label: LocalizedText }[] })
interface ExtensionColumn extends Keyed,
  Pick<DataTableColumn, "minWidth" | "grow" | "priority" | "overflow" | "align" | "card"> { header?: LocalizedText }
extendSchema(contractSchema, fields)  // schema.extend: нові поля проходять перевірку
withMockValues(records, fields)       // фікстури: запис № i — mockValues[i % n]
extensionValue(record, id): unknown   // поле розширення з запису модуля
useExtensionFields(fields)            // { text, column, entry } мовою інтерфейсу

// templates/object-page
interface RecordSlotProps<T> { record: T; resource: string }
interface ExtensionSection<T> { id: string; title: LocalizedText; component: ComponentType<RecordSlotProps<T>> }
interface ExtensionAction<T> { id: string; component: ComponentType<RecordSlotProps<T>>; access?: string }
useRecordSlots({ record, resource, sections, actions })  // → { sections, actions } для злиття
```

Правила злиття:
- порядок — `hide`, далі `add`, далі `move`; кілька нових на одному місці стають у порядку `add`;
  орієнтира немає (сховано, невідомий ключ) — новий елемент стає в кінець, переставлений і
  замінений лишаються на місці;
- ключі модуля в `hide`, `move` і орієнтирах `place` — об'єднання `K` у типі розширення:
  `applyKeyedChanges` звіряє його з ключами списку модуля (`T["id"]`), тож перейменований чи
  видалений ключ TypeScript показує у файлі розширення; під час роботи невідомий ключ (дані від
  сервера) пропускається;
- ключ модуля в `add` — заміна елемента модуля (на його місці чи за `place`): ключі в списку не
  повторюються, навіть коли оновлений модуль додав елемент із ключем, який проект уже додав сам.
  Заміна — для секцій і дій; колонку чи поле шапки модуля не замінити, бо поле розширення не може
  мати ключ поля модуля (зміна властивостей елемента без заміни — крок 1.4);
- `locked` — ключі, які розширення не ховає й не замінює (переставити можна): обов'язкові поля
  контракту, номер-посилання на картку;
- помилка розробника — виняток під час збирання, а не тихий пропуск: поле розширення з ключем поля
  модуля, два поля з одним ключем, колонка чи поле шапки без опису поля, невідомий тип поля;
- значення полів розширення в записі — `unknown` (`ExtensionValues`), читаються через
  `extensionValue`: тип запису модуля їх не знає, а модуль із масивами й вкладеними об'єктами не
  мусить узгоджувати з ними свій тип;
- компонент слота — у своїй межі помилок (`ErrorBoundary`): збій компонента проекту не валить
  картку модуля, секція показує помилку з повтором, дія зникає;
- `access` дії — дія ресурсу модуля (`edit`, не `invoices:edit`): без права дії не видно
  (`PermissionGate`); показати її неактивною з причиною (SPEC §8.4) компонент може сам
  (`useCanAccess` і `DeniedAction`).

Модуль (зразок — рахунки демо, `apps/demo/src/pages/invoice-extension.ts`; розширення проекту —
`apps/demo/src/extensions/K2-invoices.ts`, поля в `K2-invoices-fields.ts`, компоненти слотів у
`K2-invoices-slots.tsx`):
- тип розширення модуля — поля й набори змін із ключами модуля: `{ fields?, columns?:
  KeyedChanges<ExtensionColumn, ColumnId>, recordFields?: KeyedChanges<Keyed, FieldId>, sections?:
  KeyedChanges<ExtensionSection<Record>, SectionId>, actions?: KeyedChanges<ExtensionAction<Record>,
  ActionId> }`, де `Record` — тип запису контракту модуля;
- модуль перетворює дані на елементи шаблону (`useExtensionFields().column` і `.entry`,
  `useRecordSlots`), зливає їх зі своїми (`applyKeyedChanges`) і розбирає запис схемою
  `extendSchema(contractSchema, extension.fields)`; моки — `extendSchema` і `withMockValues`;
- шаблони отримують уже злиті списки: List Report — колонки, фільтри, вкладки й дії (ADR-0022),
  Object Page — `header: { title, status, fields, actions }` і `sections: { id, title, content }[]`
  (ADR-0019);
- файл розширення експортує дані, а компоненти слотів лежать поруч окремим `.tsx` (правило Fast
  Refresh: файл із компонентами експортує лише компоненти); поля — теж окремим файлом без
  компонентів, бо моки беруть лише їх: шар моків, що імпортує компоненти слотів, тягне інтерфейс, і
  збирач дробить вхідний чанк (у демо +6 КБ gzip першого екрана).

Фабрику модуля, фільтри й вкладки з полів розширення, статуси й перевизначення рядків зроблено в
кроці 1.4a (розділ «Форма типів модуля» нижче). Поля розширення у формі, зміну властивості
елемента модуля без заміни (`change`) і схему розширення в порівнянні при конфлікті зроблено в
кроці 1.4b1 (ADR-0026); демо-рахунки (`invoice-cells`, `invoice-edit-dialog`) порівнюють запис
без схеми розширення, доки рахунки не стануть модулем. Демо-рахунки поки передають розширення у двох місцях
проекту: маршрути (`lazy-pages.ts`) і моки (`mocks/handlers.ts`). Розширення підключається
статично, тож у демо воно у вхідному чанку (+1,3 КБ gzip, у межах бюджету ADR-0009): так бюджет
рахує його чесно. Важкий вміст слота проект вантажить ліниво всередині свого компонента (`lazy` і
власний `Suspense`): слот обгорнуто лише межею помилок, і без `Suspense` очікування чанка
підніметься до сторінки.

## Форма типів модуля (крок 1.4a)

Перший модуль — B1 «Контакти й компанії» (`registry/modules/B1-contacts/`, шар модулів — ADR-0025):

```ts
// extension.ts модуля — публічний API: несумісна зміна — мажорна версія кіта
interface EntityExtension<T, K extends EntityIds> {
  fields?: readonly ExtensionField[]
  columns?: KeyedChanges<ExtensionColumn, K["column"], ExtensionColumnChange> // change — 1.4b1
  filters?: KeyedChanges<ExtensionFilter, K["filter"]>   // з поля: список, так/ні, дата
  tabs?: KeyedChanges<ExtensionTab, K["tab"]>            // { id, label, filter } — фільтр даними
  form?: KeyedChanges<ExtensionFormField, K["formField"], ExtensionFormFieldChange> // 1.4b1, ADR-0026
  recordFields?: KeyedChanges<Keyed, K["field"]>
  sections?: KeyedChanges<ExtensionSection<T>, K["section"]>
  actions?: KeyedChanges<ExtensionAction<T>, K["action"]>
}
interface ContactsExtension {
  organizations?: EntityExtension<Organization, …> & {
    statuses?: KeyedChanges<ExtensionStatus, OrganizationStatus>   // lib/statuses
  }
  contacts?: EntityExtension<Contact, …>
  strings?: { uk?: MessagesOverride<ContactsMessages>; en?: MessagesOverride<ContactsMessages> }
}
createContactsModule({ basePath, extension }) // → { id, paths, routes, nav, resources, preload }
createContactsMocks({ extension })            // лише ContactsMockExtension: fields і statuses
```

- Розширення передається один раз — у фабрику; сторінки модуля беруть його з контексту модуля.
  Моки отримують ту саму частину даних окремо (`ContactsMockExtension`), бо шар моків не імпортує
  компоненти слотів.
- Статус розширення — `{ id, label: { uk, en }, tone, icon?, mockEvery? }`; ключ модуля в `add` —
  перейменування чи інший тон; `hide` ховає з вибору й вкладок, але схема й бейдж його знають.
- `strings` — глибоке часткове перевизначення рядків модуля за ключами `i18n/uk.json`; ключа, якого
  немає, TypeScript не пропустить.
- Фільтр вкладки йде в запит поверх фільтрів панелі (`listQueryFilter`, ADR-0017): вкладка з тим
  самим ключем, що й фільтр панелі, перекриває його, і чип панелі на ній нічого не змінює. Для
  вкладки розширення краще поле без фільтра панелі.
- Ключі модуля для `hide`, `move`, `place` — типи `OrganizationColumnId`, `ContactTabId` тощо;
  назву в списку (посилання на картку) модуль закріплює (`locked`).
- Приклад проекту — `apps/demo/src/extensions/B1-contacts.ts` (поля в `B1-contacts-fields.ts`,
  вкладка «Нотатки» — окремим лінивим компонентом).

## Доповнення: крок 1.7 — цикл оновлення (19.10.2026)

Зміна B1 за звітами тестового проекту (кроки 1.5b і 1.6, `docs/WAVE-1.md`) — лише сумісні
доповнення типу розширення, тож мінорна версія (v0.3.0), а файл розширення проекту при оновленні
не змінюється:

```ts
interface EntityExtension<T, K extends EntityIds> {
  // …як вище, плюс:
  detailRows?: Pick<KeyedChanges<Keyed, K["detailRow"]>, "hide"> // рядки «Подробиць» / «Реквізитів»
  history?: boolean                                              // false — без журналу «Історія»
}
// lib/statuses: `change` статусу модуля без заміни — підпис, тон, іконка
type ExtensionStatusChanges<K> = KeyedChanges<ExtensionStatus, K, Pick<ExtensionStatus, "label" | "tone" | "icon">>
// індекс модуля: типи для файлу розширення й компонентів слотів
export type { Contact, Organization, ExtensionField, ContactDetailRowId, OrganizationDetailRowId }
```

- `detailRows` поки лише ховає (`hide`): бекенд без посади чи сегментів не показує порожніх рядків.
  Переставити чи додати рядок з поля розширення — сумісним доповненням, коли знадобиться.
- `history: false` прибирає «Історію» з картки цілком (і вкладку на вузькому екрані), а не
  показує «Подій ще немає» для бекенду, який журналу не веде.
- `change` статусу лишає решту від модуля: зміна тону чи іконки в модулі доходить до проекту з
  оновленням (раніше назву міняли через `add` з тоном наново). Схований статус показується на бейджі
  зі змінами `change`.
- Ключ `detailRow` доданий у `EntityIds`. Індекс модуля `EntityIds` і `EntityExtension` не
  експортує, тож для проекту (типи з індексу) доповнення сумісне; зламався б лише код, що сам
  параметризує `EntityExtension` своїми ключами через внутрішній файл `extension.ts`.
- Тип `statuses` тепер `ExtensionStatusChanges<K>` (з `change`). Значення старого типу
  `KeyedChanges<ExtensionStatus, K>` він приймає, а навпаки — ні: код проекту, що читає
  `extension.organizations.statuses` у змінну зі старою анотацією, переходить на
  `ExtensionStatusChanges<K>` з `lib/statuses`.

Умови оновлення без ручного зведення, які показав цикл (п. 6; тестовий проект оновився з v0.2.0 на
v0.3.0 у кроці 1.7b):

- Реєстр збирається з тегу локально: тег — архівом одним запитом (`gh api …/tarball/vX.Y.Z`), далі
  `shadcn build`, і `shadcn add` бере елементи з файлів. Напряму з приватного GitHub CLI робить на
  модуль сотні й тисячі запитів `gh api` (годинний ліміт особистого токена — 5 000), кожен з
  тайм-аутом 15 с і без повтору: у кроці 1.7 усі три спроби впали — двічі тайм-аут одного запиту
  (перша спроба v0.3.0 — після 748 запитів), раз 422 при розв'язанні тегу (рішення власника
  19.10.2026 — збирати з тегу локально). Архів тегу важить ~175 МБ (здебільшого
  `docs/screenshots`), але це один запит без тайм-ауту CLI. З v0.3.1 скриншоти в архів не входять (`.gitattributes`, `docs/screenshots/** export-ignore`): ~1,5 МБ.
- Список змін — `add --dry-run` (`--diff` без шляху показує лише перші п'ять файлів), застосувати —
  `add --overwrite --yes` (інакше CLI питає про кожен змінений файл).
- CLI shadcn у проекті — закріплена версія, та сама для встановлення й оновлення.
- Директива `"use client"` дає зміни, яких у кіті немає, і версія CLI тут ні до чого. CLI 4.22.0
  (`@shadcn/registry` 0.2.0) при `"rsc": false` шукає директиву регулярним виразом із прапорцем
  `g`, а він пам'ятає позицію між файлами з директивою: з кількох таких файлів поспіль її прибирає
  лише кожен другий, і який саме — залежить від набору й порядку файлів у команді. У 1.7b 28
  файлів змінились лише цим рядком (у 13 директива з'явилась, у 15 зникла; у Vite вона нічого не
  робить), 22 — справжніми змінами тегу. Повторний `add` з тим самим набором елементів нічого не
  змінює. Прибрати директиву з файлів кіта — крок fix-use-client (вікторина 20.10.2026): з v0.3.1 її у файлах кіта немає (ADR-0006, доповнення fix-use-client), при оновленні з v0.3.0 вона один раз зникає з файлів, де ще стоїть, далі набір і порядок елементів на результат не впливають.
- У файлах кіта немає керівних символів у рядках (`\u0000` CLI записував справжнім NUL, і git
  бачив файл двійковим; з v0.3.0 — текстом).

## Доповнення: крок 1.7c — несумісна зміна типу розширення (20.10.2026)

Пробна несумісна зміна (вікторина 19.10.2026: пробна гілка без мерджу й тегу): у B1 ключ
`recordFields` перейменовано на `headerFields` на гілці кіта `wave-1/1.7c-breaking-trial`, тестовий
проект поставив модуль із цієї гілки (гілка `1.7c-breaking-trial` в `erp-ui-pilot`). TypeScript
показав 3 помилки у 2 файлах розширення, правка — 2 рядки; файли модуля й кіта оновив `add`, руками
не правились ні вони, ні адаптер (звіт — `docs/WAVE-1.md`, «Зроблено 1.7c»). Мажорна версія й
розділ «Як оновити розширення» — рішення п. 6; нижче — як це зроблено в 1.7c, порядок для
наступних несумісних змін (уточнення п. 6, не нове рішення):

- **Що несумісне.** Зміна типу розширення модуля (`<Модуль>Extension` і типи з його індексу), після
  якої файл розширення, що компілювався, перестає компілюватись: перейменований чи прибраний ключ
  розширення, перейменований ключ елемента модуля в `hide`, `move`, `change`, `place`, звужений тип
  значення, нове обов'язкове поле. Також — зміна поведінки, яку проект не помітить з помилки
  TypeScript (ключ той самий, а робить інше). Доповнення (новий необов'язковий ключ, новий ключ
  елемента) — сумісне, мінорна версія (доповнення 1.7).
- **Версія.** Мажорна (CLAUDE.md, правило 8): тип розширення — публічний API модуля, навіть коли
  змінюється один модуль.
- **`CHANGELOG.md`.** У розділі версії — підрозділ «Як оновити розширення» перед списком змін:
  1. що змінилось і навіщо, одним абзацом;
  2. що покаже TypeScript — справжній вивід `tsc` (код і текст помилки), знятий на тестовому
     проекті, а не передбачений: у 1.7c передбачений текст для контактів розійшовся зі справжнім
     (TypeScript називає тип, де оголошено ключі, — `EntityExtension<Contact, ContactIds>`, а не
     псевдонім `ContactPeopleExtension`);
  3. як поправити — дія для кожного виду помилки;
  4. приклад «було → стало»;
  5. що перевірити: `pnpm typecheck` без помилок, пошук старої назви в `src/` порожній, тести й e2e
     екранів, яких стосується зміна.
- **Перед випуском.** Демо кіта й `consumer-smoke` — на новій формі; тестовий проект пілота ставить
  модуль із гілки кіта (реєстр із гілки локально, `docs/using-erp-ui.md`, розділ 8) і проходить свої
  перевірки після правки лише файлів розширення; вивід `tsc` звідти — у `CHANGELOG.md`.
- **Що TypeScript не знайде.** Старий ключ в об'єкті з типом розширення (анотація чи `satisfies`) і
  в об'єкті лише зі старим ключем TypeScript показує. Об'єкт без типу в змінній, де поруч є інші
  ключі розширення, проходить мовчки, і налаштування просто перестає діяти. Тому файл розширення
  оголошує об'єкти з типом (так у посібнику й тестовому проекті), а розділ «Як оновити розширення»
  вимагає пошуку старої назви.
- **Підказки нової назви від TypeScript немає**, коли назви надто різні («Did you mean…» лише для
  схожих): нову назву проект бере з розділу «Як оновити розширення».
- **Не вирішено: перехідний період.** У 1.7c перевірено лише перейменування одразу в мажорній
  версії. Інший спосіб — одну версію модуль розуміє обидві назви, стара позначена `@deprecated`
  (редактор її закреслює, збірка не падає), а прибирається в наступній мажорній. Вибір — при першій
  справжній несумісній зміні (вікторина 20.10.2026).
- **Автоматичної перевірки несумісності в кіті поки немає:** демо її не ловить, бо його розширення
  правиться в тому самому PR. Незмінний файл розширення з усіма ключами в `pnpm typecheck` — у списку
  хвилі 1+ (`docs/WAVE-0.md`, вікторина 20.10.2026).

## Доповнення: крок A2a — поле «запис із довідника сервера» (25.10.2026)

Новий тип поля розширення (ADR-0030), лише доповнення — типи полів тепер у
`lib/extension-field-types`, а імпортуються, як і раніше, з `lib/extension-fields`:

```ts
type ExtensionField = …
  | { type: "record"; resource: string; labelField: string; descriptionField?: string;
      filter?: Readonly<Record<string, string | readonly string[]>>; mockValues?: (string | null)[] }
useExtensionFields(fields)  // + display(field, value): ReactNode — запис — назва з сервера
                            // + displayEntry(item, record): { id, label, value: ReactNode } — шапка
                            // entry() і text() — як були: текст, для запису — id
extensionAuditOptions(language, fields, recordTitle?)  // журнал моків — назвою запису
```

У записі — `id` запису довідника; колонка, шапка (`displayEntry`), форма (`erp/record-picker`) і
фільтр панелі (`kind: "record"` в `lib/filters`) працюють з ним без коду модуля: модуль не знає
типів полів розширення. Модулі кіта (B1) ставлять у шапку `displayEntry()` замість `entry()`.

## Розглянуті варіанти

- **Правка файлів модуля з позначкою `local override`** (SPEC §3.3 до цього рішення): працює для
  одного компонента, але для модуля кожне оновлення в кожному проекті — ручне зведення.
- **Модуль як npm-пакет із налаштуваннями:** оновлення простіші, але це суперечить SPEC §2 №2–3:
  код копіюється в проект, без runtime-залежностей від приватних пакетів, клієнт отримує весь код.
- **Патчі поверх модуля** (patch-package, git-патчі): ламаються, щойно змінюються сусідні рядки, —
  те саме ручне зведення.
- **Генерація модуля під клієнта** (CLI питає поля й створює код): зручно один раз, далі оновлення
  знову ручні.
- **Форк модуля в кожному проекті:** оновлень немає взагалі. Лишається як аварійний вихід (п. 7).
